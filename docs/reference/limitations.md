# Known limitations and constraints

- `InMemoryUnitOfWork` has, **by design**, no durable persistence step: aggregates live in the in-memory repositories and `SaveChangesAsync` boils down to the (real and ordered) dispatch of domain events. A durable adapter would replace this adapter as a whole — there is no longer any EF migration promise in the code.
- **Execution state persistence (R3.8)**: by default, crew execution states (`ICrewExecutionStateManager`) are **in-memory only** (no recovery after a crash). Durable persistence is **opt-in**: choose a checkpointing state store — the `Orkeon:Checkpointing` section (`Enabled`, `Store` json, sqlite or postgres), read by `orkeon run` and `orkeon-host`, or `AddOrkeonCheckpointing(configuration)` / `AddOrkeonSqliteCheckpointing` / `AddOrkeonPostgresCheckpointing` in a host written in C# — **and** enable `AddCrewExecutionStatePersistence(...)` (or the `Orkeon:ExecutionState:Persistence` section). A failed or killed run is resumed with `orkeon run --resume <id>|latest` at the granularity of the **task**: every task a run completes is checkpointed as it ends, and a resumed run answers those from the checkpoint without calling the model. The decisions of the manager of a Hierarchical or Autonomous crew are **replayed live** on a resume (only the tasks are kept: the manager is asked again to assign and review), a decision task (`decision:`) is asked again in Sequential and Parallel (Graph checkpoints the route a decision took and replays it), and a task still running when the process died runs again from its start. A task edited between the runs (its description or expected output as the run's variables fill them, so a changed `--var` counts, its agent or its dependencies) is run again, and so is every task that runs after it, since what they would read of its output is stale; the host logs one warning naming it. `--resume latest` takes the most recent run of the crew that is not completed (a newer completed run does not hide an older failed one); a run still marked `Running` is **not** taken over by `latest`, since the store holds no lease and it may be alive in another process: the refusal names its id, and `--resume <id>` takes it over. A session waiting for an answer, or marked failed, is refused by `latest`, and by its id, only when the run history proves its owner alive (recorded as running with a live process on this host, or run on another host); with no history record of it, it is resumed. Without a lease, nothing else stops two processes from resuming the same run by its id at once. A run is resumable from the place it was started from: moving or renaming the checkout (or the crew file) changes the crew key and orphans its earlier runs. Two limits of the run identity: the A2A task id and the API's are **not** unified with the run id yet (`StateStoreA2ATaskStore` stays on its own `__a2a__` key and task ids, FWK-14). The crew key of a session is the crew's name, the virtual path of its file and a short digest of that file's full path (two folders both read `/crew` to the virtual file system), so two crews of one name never share a session. `Orkeon:Checkpointing:Store` without `Enabled: true` is ignored and the host says so at its start. Once enabled, states are persisted at every transition and reloaded/reused after a restart — see [Opt-in subsystems](./opt-in-subsystems.md). v1 limits: metadata persisted as invariant strings, `ToolsUsed` not persisted.
- The framework targets .NET 10 — its version is defined in `src/Directory.Build.props`. **.NET 11** (GA on 2026-11-10) is not a target yet: `ci.yml` builds and tests the solution with the 11.x SDK (preview channel, non-blocking until GA) as an early warning, and both dotnet tools (`orkeon`, `orkeon-repl`) roll forward to a newer major runtime (`RollForward=Major`) so a machine with only .NET 11 installed can run them. The target framework, `global.json` and the container base images move on GA day, not before.
- **The functional scope is frozen** at 16 LLM providers (fourteen vendors and two aggregators — OpenRouter and Mammouth AI, the first motivated exception to the freeze, integrated documentation-first and campaigned on 2026-10-07, LLM-08), 124 built-in tools (the e-mail family is the second motivated exception, decided by the owner on 2026-09-26; Gmail and Hotmail through Graph are campaigned, Outlook over IMAP and SMTP has not been run; the drive family — Google Drive and OneDrive — is the third, decided on 2026-10-17; a first campaign pass ran on 2026-10-24 (DRIVE-07) and led to the `drive_search` fixes, but the campaign is not closed; the `firefox` tool is the fourth, asked by the owner on 2026-11-06) and 6 memory stores until real users ask for more: a single maintainer carries the whole surface, and every addition is a permanent cost. No 17th provider: endpoints that speak the OpenAI dialect need no provider (point `Llm:BaseUrl` at them); tools are written in `.ork.ts` scripts or plugins. The rule and what remains welcome are in [CONTRIBUTING.md](../../CONTRIBUTING.md#the-scope-is-frozen).
- **No batch API (FWK-05)**: the providers' asynchronous batch endpoints (Anthropic Message Batches, OpenAI Batch, and the like) are not driven. A batch answers within hours and takes no interactive tool calling, so it cannot carry the agentic loop (call, tool result, call), and serving it would need a deferred execution mode that does not exist. A run that wants the cheaper batch price has no path to it; a profile's [fallback](../architecture/llm-providers.md#profile-fallback) does not use it either.
- **`LlmConfig.ApiKeySecretName` is reserved, not resolved.** The framework never turns a secret *name* into an API key: every provider guard and every request path reads `LlmConfig.ApiKey`, so a config carrying only `ApiKeySecretName` is unconfigured and every call against it answers that an API key is required. The `*WithSecret` factories (`WithDefaultModelSecret`, `ClaudeWithSecret`) record the name and nothing more. A host that keeps its keys in a secret store resolves the name itself and assigns the result to `ApiKey`; the supported paths for supplying it are the settings file (`Llm:ApiKey`), the environment (`ORKEON_Llm__ApiKey`), and — to keep the key out of the file — the variable the file names (`Llm:ApiKeyEnvVar`, and per profile `Llm:Profiles:<name>:ApiKeyEnvVar`, read in the process environment and then the Windows user scope; see [configuration](./configuration.md#the-api-key-apikey-apikeyenvvar)). `ApiKey` carried an `[Obsolete]` attribute steering callers to `ApiKeySecretName`; it was removed because it pointed at a path that does not exist.
- LLM streaming is uniform at the framework boundary: all 16 providers inherit the SSE/NDJSON streaming reader from `HttpLlmProviderBase` (`IStreamingLlmProvider`). `SupportsStreaming` is **not** an unconditional `true`: it follows whether the provider is actually usable (an API key when the vendor needs one, plus the resource endpoint for Azure), so an unconfigured provider declares `false` and every caller branching on the capability takes the buffered path — which returns the explicit "API key is required" answer — instead of an SSE branch that would end without a single chunk. The remaining per-provider exception is Ollama's `/api/chat` (see the Ollama entry below). Since LLM-12 a streamed call runs whole under `Llm:TimeoutSeconds` and, when set, under `Llm:StreamIdleSeconds` between two chunks; two edges remain: on the headers phase the same timeout runs twice (`HttpClient.Timeout` and the stream budget, started a moment apart), so an elapsed one may cost one extra connection attempt before the failure is reported; and the text-only streams (`GenerateStreamingAsync`), which carry no metadata, cannot flag a stream closed without its finish marker after some text — they end normally, where the chat stream carries `stream_truncated`
- **The `mock` provider streams in one chunk** (FWK-02): `Provider: mock` (`orkeon run --llm-mock`) emulates streaming by sending the whole answer as a single content event before the completed response, and declares no native streaming; it matches the last user message of a call, not the whole conversation, and it has no capability flag for native tool calling to declare — the framework has none: its tool calls are an OpenAI-shaped response body (`choices[0].message.tool_calls`), which the host's default tool-calling strategy reads, as it reads Ollama's, and a crew with a real tool runs through it end to end. A host that registers another strategy reads that body with it, and so a mock tool call may not parse there. The folder of its responses file is an internal mount: it may hold neither the crew nor the script.
- **A cassette freezes the model's answers, not the run** (FWK-11): `--llm-record` and `--llm-replay` ([guide](../guides/testing.md)) file each call under a hash of the profile, the messages, the system message, the tools and the tool mode, the response format and the grammar, so any change of a prompt, a tool or the format is a replay miss (`ReplayMissException`, never a network call) until the cassette is recorded again. Tools run again on a replay, and embeddings and memory are not recorded. The key also holds the model and the sampling options (temperature, top-p, seed, penalties, stop sequences, max tokens, thinking), so changing one is a miss too. A cassette is redacted only for the configured key and the listed patterns (in a streamed call, over the deltas joined, so a secret cut between two deltas is masked too), and the key is computed over the redacted form; a secret that matches no pattern is neither masked nor mirrored in the key: check a cassette before committing it. Two agents asking the same key at the same moment take the recorded answers in the order they ask, so a run whose identical parallel calls differ in order may swap them.
- **The token meter counts generation calls — every one, and only those**. `cost.updated` and `run.finished` sum the calls of a run through the one metering decorator every provider is wrapped in: agent turns and their retries, the hierarchical manager, the planner, the RAG pipelines, the memory services, LLM judges and `ctx.llm.*` calls. **Embedding calls are not counted** — the vectors of RAG ingestion and retrieval, of `semantic_search`, of RaggableTree indexing and of a crew's memory (what it stores and what it recalls) come from the embedding ports, which the ↑/↓ figure does not see. Two consequences of where the meter sits: a provider a host registers by hand is metered only through `AddOrkeonLlmProvider` or `AddOrkeonLlmProfile`, or handed to a crew's manager with `CrewBuilder.WithManagerLlm` or to its planner with `CrewBuilder.WithPlanningLlm` (an `IChatClient` that is not built on an Orkeon `ILlmProvider` is not metered at all), and a text-only stream, which carries no usage, is counted at its end as an estimate — reported under `estimatedTokens`, never priced.
- **A2A in the shipped binaries**: `orkeon-host` serves the crews `Orkeon:Host:A2A` exposes — one skill per crew, a task being a run of that crew through the runner a chat message goes through (its mounts, its concurrency bound, the host's deadline), the start refused when the listener would reach beyond the loopback without authentication — see [Service host](../architecture/service-host.md#5-other-agents-a2a); it keeps no task records (`GET /a2a/tasks/{id}` answers `501`). The run API and the health probes are a separate listener, off unless `Orkeon:Host:Api:Enabled` — see [the host API](./host-api.md): `POST /runs/{id}/input` answers a run's pending human-input question (`200 delivered` to a held run, `202 recorded` for a suspended one), and its idempotency keys survive a restart only through the run history. `orkeon run` and the REPL serve no A2A: a single run has nothing to listen for. `orkeon-host` also connects the `MCP:Servers` at startup, like `orkeon run` and `orkeon-repl` — see [MCP integration](../architecture/mcp.md). A C# host that calls `AddOrkeonA2A` gets a server started with the generic host (`EnableServer`) whose router runs the agent a task names — see [A2A conformance](./a2a-conformance.md#activation).
- **Deliberately-minimal DI defaults** — `IKnowledgeStore` (in-memory, non-persistent; its `SearchAsync` ignores the query) and `IAgentExecutionService` are stand-ins that each announce themselves with a **one-time Warning naming the remediation**; nothing calls an LLM or persists implicitly. Full inventory and replacement gestures: [Default behaviors](../getting-started/default-behaviors.md)
- Custom tools must implement `IBaseTool` or inherit from `ToolBase<TReq,TRes>`. Runtime plugin loading **exists** (opt-in `AddOrkeonPlugins(...)` — a `plugin.json` manifest per plugin folder, isolated collectible `AssemblyLoadContext`s, see [Plugins](../architecture/plugins.md)); v1 limits: loaded assemblies run with full trust (no sandbox), and there is no hot-reload
- Several subsystems (A2A, monitoring backend, NIST, DLP, tool rate-limiting, key rotation, benchmarking, multi-modal validation, kickoff hooks, **RAG subsystem** since RAG-01/C6 — `AddOrkeonRag` + `AddOrkeonRagTools` since RAG-02, plus the RAG opt-in `AddOrkeonOnnxReranker` since RAG-04; the web-fallback transport of RAG-06 is wired by `AddOrkeonRag` itself and governed by configuration) are **opt-in**: they are no longer registered by `AddOrkeonInfrastructure()`/`AddOrkeonApplication()` and are enabled through their dedicated extension — see [Opt-in subsystems](./opt-in-subsystems.md)
- A2A — task persistence is **opt-in** (PUB-08): register a checkpointing state store plus `AddOrkeonA2ATaskPersistence()`, and `GET /a2a/tasks/{id}` answers `200` with the recorded lifecycle (`404` for unknown ids) while `DELETE` interrupts a task the agent is still working on (it ends `Cancelled`), answers `409` for a finished one and `404` for unknown ids. Without the opt-in, `GET` keeps returning an explicit `501` rather than fabricating state. The broader v1.0 spec gaps (bindings, push notifications, 9-state lifecycle, `A2A-Version`) are inventoried in the [A2A conformance matrix](./a2a-conformance.md).
- A2A mTLS — `A2AClient` loads the client certificate (`A2ASecurityOptions.ClientCertificatePath`) and always applies full server-certificate validation — there is deliberately **no** accept-any-certificate opt-out; a self-signed or local-dev server pins its CA via `TrustedCertificateAuthorities`. Server side, when `RequireMutualTls = true`, `A2AServer` only accepts client certificates that **chain to one of the `TrustedCertificateAuthorities` or match a pinned `TrustedClientCertificateThumbprints` entry** (403 otherwise) and **refuses to start when no trust anchor is configured** (fail-closed). Certificate revocation is not checked (private CAs without CRL/OCSP endpoints are assumed). Client-side CA pinning only vouches for an unknown chain — a host-name mismatch is never bypassed. When `AllowedAuthSchemes` is set, a request is accepted only with a credential its scheme's validator accepts (401 otherwise): a `Bearer` token validated by a registered `IAuthenticationProvider` (`A2A:Security:AzureAD` / `A2A:Security:Oidc`), an `ApiKey` matching a secret named in `ApiKeySecretNames`; the server refuses to start when a declared scheme has no validator. `A2AClient` sends `Authorization: <ClientAuthScheme> <secret>` when `ClientAuthScheme` and `ClientCredentialSecretName` are set, the secret read through `ISecretProvider` on every call. Real mutual TLS termination requires an HTTPS binding of `HttpListener` (HTTP.sys reservation / server certificate) configured at the host level; the discovery endpoint `/.well-known/agent.json` remains public.
- **Semantic agent selection** (`OrkeonApplicationOptions.AgentSelectionStrategy = Embedding`) inherits the real embedding resolution chain since RAG-02/C5: the hash-based `SimpleEmbeddingService` has been **removed**, and the default `IEmbeddingService` adapts the `IEmbeddingProvider` port (**local BGE** when `AddOrkeonLocalEmbeddings()` is registered → **remote provider** from `Orkeon:Embeddings` → **fail-fast** `InvalidOperationException` at first use with an actionable message). There is no silent non-semantic fallback anymore: without any embedding provider the `Embedding` strategy fails loudly — either configure one, or prefer the `Skill` strategy (lexical matching, no dependency) or the `FirstFit` default (first available agent)
- **Fixed since RAG-01, re-based in RAG-02** — the RAG path no longer degrades silently: the ingestion pipeline (`Orkeon.Rag`) embeds chunks **at ingestion** and the document store searches by scored vector similarity (similarity scores survive end-to-end to `ScoredChunk`), and the `IEmbeddingProvider` port resolves as **local BGE provider (when `AddOrkeonLocalEmbeddings()` is registered) → remote provider from `Orkeon:Embeddings` → fail-fast** (`InvalidOperationException` on first use with an actionable message). `HashBasedEmbeddingProvider` is a test double only — it is never resolved implicitly
- **Native tool calling — Ollama (lifted in LLM-07)**: `OllamaLlmProvider` now reaches `/api/chat` — and is wired with the native OpenAI strategy — whenever the conversation declares tools, replays tool calls, or carries a non-text part (an audio or file part is then refused with `NotSupportedException`, as on Anthropic, and on OpenAI for a model without audio input). It reshapes Ollama's response (`message.tool_calls` with `arguments` as a JSON **object**, no `choices` array) into the OpenAI body the framework's single parser reads (`choices[0].message.tool_calls`, `arguments` as a JSON **string**), and assigns positional call ids since Ollama issues none. Remaining limits: everything else — plain conversations, single-prompt generation — still uses `/api/generate`, so the **text fallback protocol stays in charge for models without tool support** (a streamed call takes the same endpoint the buffered one would); and images must be supplied as bytes, since Ollama takes bare base64 payloads and never fetches a remote URL.
- **RAG `adaptive`/`corrective` profiles — the LLM-dependent nodes degrade offline**: since RAG-06 the Adaptive-RAG `Iterative` route delegates to the **`corrective` graph pipeline** (the RAG-05 documented fallback to `quality` is lifted; the `route` step traces `delegate=corrective` and `RagTrace.Route` carries the decision). Remaining honest limits: the default complexity classifier is the deterministic heuristic; the `llm` classifier requires a registered `IChatClient` (without one it falls back to the heuristic with a warning); and **without a real LLM the corrective graph cannot bridge a vocabulary gap** — in `--offline` evaluation the extractive stub feeds `rewrite_query`/`evaluate`/`check_groundedness`: the grader's tolerant parser fishes grade words out of the echoed passages (deterministic verdicts driven by the one grade word the golden corpus happens to contain; the groundedness fallback stays safely `grounded`), and a triggered rewrite degenerates to the stub's fixed prefix — one meaningless probe shared by every case — so the offline `corrective` numbers measure the loop's guard rails plus that degradation, not rewrite quality, and can land **below** `quality` (measured table and analysis in `examples/rag/eval/README.md`; the end-to-end mechanism — evaluator verdict → rewrite → recovered citation on the seeded q-007 case — is proven by `CorrectiveRagMechanismSlowTests` with a scripted LLM, labelled as such). Same offline note as before for the LLM-backed query transformers (`multi-query`/`rag-fusion`/`hyde`): the measured offline path is `QueryTransform.Mode=none` + heuristic routing.
- **RAG profiles `balanced`/`quality`/`adaptive` require the ONNX reranker packages**: their presets enable the cross-encoder rerank stage. The three shipped binaries — `orkeon`, `orkeon-host` and `orkeon-repl` — register it. A C# host of its own that does not reference `Orkeon.Rag.Onnx` + `Orkeon.Rag.Onnx.Model` and call `AddOrkeonOnnxReranker()` fails **at the rerank stage of the first query** under those profiles (`Unknown reranker 'onnx'`, naming the rerankers it knows). `fast` (the default) and `corrective` (the graph corrects by looping, no linear rerank stage) work without the ONNX packages. `adaptive` needs them because its `SingleShot` route delegates to `balanced`.
- **ONNX native runtime — the suites that load it**: two test suites load the ONNX Runtime native library — `tests/tools/Orkeon.Tools.Embeddings.Local.Tests` (local BGE-micro-v2 embeddings) and `tests/rag/Orkeon.Rag.Onnx.Tests` (ms-marco cross-encoder reranker) — so they need a platform where that library loads. Until 2026-09-07 this entry also described a SIGSEGV (exit 139) that took the process down *after* the Embeddings.Local tests passed, called it a teardown artefact of the native runtime (PUB-17 / SONAR-14), and had `ci.yml` and `publish.yml` tolerate exactly that shape. **It was not a teardown artefact.** `Dispose_Releases_Embedder` called `EmbedBatchAsync` on a disposed provider, and the provider — which set a `_disposed` flag it never read — dereferenced the freed native session: undefined behaviour that surfaced as a bogus `OnnxRuntimeException` on a warm heap and as a process-killing SIGSEGV on a dirty one, sometimes before a single result had been reported. The tolerance could not have caught that either, since the accounting it compared came from the crashed process itself. `LocalEmbeddingProvider` now throws `ObjectDisposedException` from `EmbedBatchAsync` and `Dimensions`; the suite exits 0 (17 consecutive runs on 2026-09-07), the two CI steps are plain `dotnet test` runs again, and `integration.yml` no longer excludes the project. Both suites were also measured green inside a container on 2026-09-07, so the earlier instruction to run them only on a host or in CI is dropped.
- **The local embedding model reads English.** BGE-micro-v2 — the on-device model of `Orkeon.Tools.Embeddings.Local`, behind local semantic search, RAG retrieval with local embeddings, semantic agent selection and `orkeon usecases search` — was trained on English. Its WordPiece vocabulary (30,522 tokens) holds no accented letter and 244 Chinese characters: "matin", "chaque" or "résumé" reach it cut into fragments, while "morning" and "report" are whole words. A French, Spanish, German or Chinese text still gets a vector, but one much closer to noise than to meaning, so expect semantic search, and retrieval or agent selection by embeddings, to be markedly weaker outside English. `orkeon usecases search` is built around it: BM25 carries the five languages, the sheets are embedded from their English text, and meaning is fused in only for the languages where its golden set measured a gain ([CLI reference](./cli.md#orkeon-usecases)). For semantic search in other languages, configure a multilingual remote embedding provider (`Orkeon:Embeddings`).
- **Embedding providers: five, and a changed model stops the host** (FWK-25) — `Orkeon:Embeddings:Provider` takes `openai` (any M.E.AI generator), `ollama`, `mistral`, `azure-openai` and `gemini` ([providers](../architecture/llm-providers.md#embedding-providers)). Cohere, Voyage and pgvector are not shipped. Vectors depend on the model that made them, so at start the host compares the provider, model and dimensions with the fingerprint recorded at `Orkeon:Embeddings:FingerprintPath` and refuses to start when they differ: nothing is migrated, you re-embed and clear the stored vectors, then delete the fingerprint file. The guard sees the embedding settings, not the vector stores: a store that was filled by another host, or by code that built its own provider, is not checked. Every host with an embedding provider is guarded, with or without an `Orkeon:Embeddings` section, so a host that embedded under the on-device default and then names another provider is refused (a host with no embedding provider writes nothing); a host with no `/workspace` mount, or an empty `FingerprintPath`, runs unguarded with a warning. The default `MinScore` (0.6) was measured on the local model only; no remote embedding model has a measure yet.
- **`Orkeon.Tools.Embeddings.Local` rests on a pre-release of an archived upstream** — the local on-device embeddings opt-in is built on `SmartComponents.LocalEmbeddings 0.1.0-preview10148` (pinned in `Directory.Packages.props`), which is the **only** version that exists: upstream has never cut a stable release, and the repository the package's `projectUrl` points at (`dotnet-smartcomponents/smartcomponents`) is **archived** — the code moved to `dotnet/smartcomponents`, which still ships no 1.0. Waiting for a stable upstream is not a plan. The licence side is settled and documented (MIT for both the wrapper and the bundled BGE-micro-v2 weights, provenance established by hand in [`THIRD-PARTY-NOTICES.md`](../../THIRD-PARTY-NOTICES.md) sections 1-2); what remains is a **packaging** constraint: NuGet refuses to pack a **stable** package that depends on a pre-release (`NU5104`). So a stable `1.0.0` of Orkeon cannot carry this dependency inside its main package — which is precisely why this opt-in ships as its own `Orkeon.Tools.Embeddings.Local` package instead of being folded into the `Orkeon` umbrella (PUB-25). The consequence for a consumer: **referencing this opt-in pulls a prerelease dependency into your own graph**, and if you then publish a stable package of your own that depends on it, you hit `NU5104` in turn. Escape hatches, cheapest first: (a) do not reference the opt-in — the `IEmbeddingProvider` port then resolves a remote provider from `Orkeon:Embeddings` (see the semantic agent-selection entry above); (b) implement `IEmbeddingProvider` over your own embedding stack; (c) vendor the upstream inference wrapper (MIT, so this is allowed) into an assembly you control and drop the package reference. The `orkeon` / `orkeon-repl` dotnet tools and the installers are **not** affected by `NU5104` — a tool package is self-contained and its own version is what NuGet checks. **Decision (2026-09-11): the pre-release is assumed, not vendored.** `Orkeon.Tools.Embeddings.Local` will ship as a stable `1.0.0` that depends on `SmartComponents.LocalEmbeddings 0.1.0-preview10148`; `NU5104` is silenced in that one packaging project (the umbrella, `Orkeon.Tools` and the CLI never carry the dependency), a stable pack of the whole line succeeds, and the README says in one line which opt-in stays on a pre-release and why. Vendoring the inference wrapper (escape hatch (c)) remains possible for a consumer who needs a fully stable graph; it is not worth a second copy of an MIT wrapper for the framework itself.
- **RAG web fallback is double opt-in and off by default**: the corrective graph's `web_fallback` node runs only when **both** switches are enabled — `Orkeon:Rag:Corrective:WebFallback` (policy: may the graph leave the local store) **and** `Orkeon:Rag:WebFallback` (transport: SearxNG endpoint — `AddOrkeonRag` wires the transport, whose corrective-graph adapter `IWebDocumentRetriever` is registered only when enabled with a non-empty endpoint). Every fetched page is screened by `PromptInjectionDocumentValidator` before entering the working set (`Rejected` pages never enter; `Suspicious` follows the configured policy) — see [Security](../architecture/security.md)
- **E-mail tools — protocol limits** (`Orkeon.Tools.Email`, see [the guide](../guides/email.md)): Gmail was campaigned against a real account on 2026-10-04 (app password) and 2026-10-05 (OAuth2) — [what it established](../guides/email.md#what-the-gmail-campaign-established); Hotmail through Microsoft Graph on 2026-10-12 (MAIL-07). Outlook over IMAP and SMTP has not been run against a real account. A search page holds about ten messages whatever `limit` asks, being cut to a tool result: only a null `next_cursor` ends a folder. No tool returns a message's Gmail labels. POP3 reads the inbox only — no folders, marks, drafts or trash; a delete is permanent and needs the `Purge` right; a search filters on sender, the To header, subject and dates, over at most 200 messages per call. Microsoft Graph accepts 4 MB per request, about 3 MB of attachments (no upload session), and a text search goes through KQL with the marks and dates applied client-side, so a page may hold fewer messages than asked. On a custom IMAP server `raw_query` is refused (it needs Gmail or Graph), and without UIDPLUS a moved message or a saved draft comes back without its new id. Outlook over IMAP inherits Microsoft's consumer OAuth regression of 2026-09-24, which is why Graph is the default. `Send:MaxPerHour` is counted per process, a refused attempt included. The prompt-injection screen sees hidden content through a short list of inline declarations (`display:none`, `visibility:hidden`, `opacity:0`, `font-size:0`, `max-height:0`, `width:0`, `height:0`, `mso-hide:all`) and the `hidden` attribute only — text hidden by a CSS class in a `<style>` block, a 1-pixel font or white on white is neither left out nor flagged, and a plain-text part, which the agent reads when there is one, is not compared with the HTML; a body nesting elements more than 5000 levels deep is replaced by a one-line notice. OAuth token files are plain JSON — shielded from the VFS tools, not from a shell or code tool running as the same operating-system user — and `orkeon-repl` keeps no token store, so OAuth accounts work under the `orkeon` runners only. Not in this version: deleting folders, copying a message or giving it several Gmail labels, interactive approval of a send (`email_draft` is the review path).
- **Drive tools — scope and provider limits** (`Orkeon.Tools.Drive`, see [the guide](../guides/drive.md)): the owner's campaign against a real Google Drive and OneDrive (DRIVE-07) is not closed: a first pass ran on 2026-10-24 and led to the `drive_search` fixes, and no campaign report is written yet. An account sees its own "My Drive" or OneDrive only: Google shared drives and SharePoint libraries are not reached. A search on Google Drive cannot be bounded to a subtree, so its results outside the account's `Root` are dropped and a page may hold fewer items than `limit`; on OneDrive a search takes words only (`text` or `name_contains`), the other criteria being applied to what it returns, and `raw_query` is refused. An account on the `consumers` tenant (personal Microsoft accounts) deletes nothing for good on OneDrive. Google documents are read through their text export (plain text, or CSV for a sheet — its first sheet) and downloaded by export; `drive_read` fetches at most 2 MB, a larger or binary file going through `drive_download` and the file tools. The root check climbs 32 parent levels at most. Uploads stop at `MaxUploadMegabytes` (100 by default), sent in a resumable session to Google (in 8 MiB chunks above 8 MiB) and in 10 MiB chunks to OneDrive above 4 MiB. Token files are plain JSON — shielded from the VFS tools, not from a shell or code tool running as the same user — and `orkeon-repl` keeps no token store, so drive accounts work under the `orkeon` runners only. One credentials directory per run: when `Orkeon:Tools:Email:CredentialsDirectory` and `Orkeon:Tools:Drive:CredentialsDirectory` differ, the e-mail one is used. Not in this version: copying, revisions, comments, removing a share, a trial drive for the forge, a drive mounted in the VFS.
- **MCP — dual-era client/server since PUB-07**: the client probes with `server/discover` and speaks the modern stateless revision (`2026-07-28` — per-request `_meta`, version renegotiation on `UnsupportedProtocolVersionError`) or falls back to the legacy `initialize` handshake (`2025-11-25`, `2025-06-18`, `2024-11-05`; `2025-03-26` is deliberately excluded — it is the only revision mandating JSON-RPC batching, which this implementation does not speak); the server serves both eras concurrently — over stdio only, started by `orkeon mcp serve` (no HTTP transport for the server), each `tools/call` through the guarded invocation point of the agent turns, requests running at once up to `--max-concurrency` (4) and cancellable with `notifications/cancelled`, and `/output` served as read-only resources under `--expose-output` (no `resources/subscribe`, `/workspace` never), and prompts only for the tasks of the crews named by `--crew`. Honest gaps of the modern surface: `subscriptions/listen` over HTTP only (stdio notifications are heard on their own, and `tools/list_changed` re-synchronises the registered tools), crews served as tools (`orkeon mcp serve --crew`: `run_crew_<name>`, progress per task, tasks as prompts, FWK-24) recorded in the run history when it is on, but no sampling, roots or elicitation (a server request for them is answered `-32601`: sampling would call an LLM outside the run's budget, guard and cost, roots would expose physical paths, elicitation waits for durable human-in-the-loop), no multi-round-trip requests (an `input_required` result surfaces as a tool error), an OAuth client for the server (client credentials, device flow: `Auth:Type` `oauth2-client-credentials` or `oauth2-device`, FWK-16) but no authorization-code flow, no protected-resource discovery (RFC 9728) and no dynamic client registration (DCR), and the device flow is refused in `orkeon-host` (no terminal) — a server behind a static credential is reached through `MCP:Servers:<id>:Auth` (bearer or basic, read from the environment) and `Headers`; the HTTP transport is Streamable HTTP (session id, 404 re-initialisation, SSE answers read event by event, the `GET` stream with `Last-Event-ID`; the 2024-11-05 HTTP+SSE transport with a separate endpoint is not supported). Interop against the reference server (`server-everything`) runs nightly, and by hand with the MCP Inspector — [MCP interop](../guides/mcp-interop.md).
- **LanceDB** — `LanceDbMemoryProvider` now targets a remote **LanceDB Cloud/Enterprise** server (Lance REST Namespace protocol, Arrow IPC payloads); there is no local JSON store anymore. Remote API limits (details in [Memory system](../architecture/memory-system.md#lancedb-real-remote-integration)): `SearchAsync` requires an FTS index on `content` (created automatically at table creation, otherwise the server error is propagated — never simulated locally); `HybridSearchAsync` issues two server requests (`_distance`/`_score` rankings server-side) and merges the two ranked lists locally, like the official SDKs' rerankers; since the delete API does not return a counter, `DeleteAsync`/`UpdateAsync` perform a prior existence request to preserve their boolean contract; the score conversion = `1 − _distance` is only meaningful for the `cosine` metric (default)
- **The Guardian's detection is heuristic** — the input phase and the tool-result sanitizer match phrasings (`ignore previous instructions`, chat-template tokens, …): a rephrased attack passes, and an honest prompt can match — under the default `Security:Prompt:Policy = Block` it then fails its task with the pattern named (`Warn` lets it through with a warning). Tool results are tagged as data, never cleaned. Only hosts that compose `AddOrkeonApplication()` with `AddOrkeonInfrastructure()` get the guardian; an `ExecutionOrchestrator` built by hand runs unguarded unless its `Guardian` and `ToolInvocation` are set. See [Security](../architecture/security.md).
- **Decision models: one judge per phase** — TypeSafe, Liquid and Kev are `Decision` providers behind `IDecisionModel`, not 17th LLM providers: an agent cannot take one as its `llm`. The LLM judge of the guardian (`Orkeon:Guardian:Llm`, off by default) judges agent input and a task's output through the one `IDecisionModel`, with no profile of its own, and adds a model call per phase, delays a task's streaming until its output is judged, judges a long text whole in chunks of `MaxContentChars` overlapping by a quarter under `FailMode: Closed` (32 chunks at most, then the text is refused) but only the first and last half of `MaxContentChars` under `Open` (the middle is not judged), and covers crew tasks only (a scripted `ctx.llm.act` answer is not judged); a response inside a call is judged by a response stage of a decision profile (`Orkeon:Decision:Profiles`). The request stages ask about the last user message only, a re-call after the response happens once per call, and neither the stages nor the `decision` reranker set `LongContext`: a long state or many passages may exceed the provider's per-request context and fail with its limit error, a 400 `max_tokens_exceeded` ([Decision models](../architecture/decision-models.md)). Kev's extra operations (permute, separate, model list) are not wired. No cost is computed for a decision, only its usage tokens. The open d1 weights are not served by Orkeon: Liquid is reached through its hosted API.
- **A crew's memory keeps everything, recalls by vector unless the cognitive memory is enabled, and persists only in a durable store** — with `memory: true`, a crew stores the result of each task that succeeds and recalls the closest ones before each task ([Memory system](../architecture/memory-system.md#a-crews-memory-provider-and-scope)). What it does not do: there is no retention and no reset — the memory grows by one entry per successful task, run after run, and `IMemoryService.ClearMemoryAsync` clears only the current run's entries; on In-Memory it lives in RAM for the life of the process, so `orkeon run` remembers across processes only with a durable store (`memoryProvider: sqlite`, a vector database, or a durable `Memory:Provider`); the recall is a vector search, with no LLM fact extraction and no recency or importance score (CrewAI's) — unless `Orkeon:CognitiveMemory:Enabled` is `true`, which recalls by composite score and analyses what is stored at an LLM cost ([Memory system](../architecture/memory-system.md#in-a-run-fwk-04)); `MinScore` (0.6) is on the local English model's scale, where French text scores high whatever it says, and a long input variable that shares a memory's subject can lift an unrelated task over it.
- **A crew's plan is advice, made on the default profile** — with `planning: true`, a planner writes a step-by-step plan for each task before the first one, and each task reads its own plan in its prompt, in all six modes; the plan changes neither the order nor the agents (GAP-31, [Process types](../orchestration/process-types.md#planning-planning-true)). What it does not do: it plans on the crew's planning provider (C# `WithPlanningLlm`) or on the host's default profile — a YAML or `.ork.ts` crew cannot name another (GAP-19 keeps the planner there); it shows the planner neither the agents' backstories nor their knowledge nor the crew's memory, and cuts what it shows (`PlanningDefaults`); a reply it cannot read twice leaves the crew without a plan — a warning, not a failure; and on the echo provider (no `Llm` section) it skips the plan, with a warning.
- **`spawn_agent` — the script host offers it, the C# tool is host-registered** — a script's `act` is offered `spawn_agent` (`SpawnAgentScriptTool`, RT-01): it runs a named crew agent as a child under the delegation-depth and spawn budgets of the crew run (see [Scripting](../architecture/scripting.md#child-agents-spawn_agent-and-ctxspawnbackground)). The C# `SpawnAgentTool` (budget-controlled self-spawn of the autonomous mode, in `Orkeon.Infrastructure`) is a different class and stays host-registered: no shipped composition root — neither `orkeon run` nor the REPL — puts it in the tool registry, and a C# host that wants self-spawn registers it explicitly with an `IAgentFactory`. See `docs/tools/inventory.md` and `docs/orchestration/autonomous.md`.
- **Per-execution mount namespaces are entered by `orkeon-host` and the forge's trial only** — `IFileSystemScope` / `AsyncLocalFileSystemScope` (Domain) hand one execution flow its own `FileSystemRegistry`, and `FileSystemService` consults that ambient override on every operation, so two crews running in the same process can each address their own `/output` over different physical folders — the registry's duplicate-virtual-path rejection is per instance, never global. `orkeon-host` enters a namespace per hosted crew, from `Orkeon:Host:Crews:*:Mounts` (`CrewRunner`), and the forge's trial enters one made of the folders its session confirmed (`ForgeTrialScope`). Every other entry point — `orkeon run`, the rest of `orkeon forge`, `orkeon rag`, `orkeon-repl` — runs against the boot registry, one flat mount set per process whose virtual paths must be globally unique, which is why they reserve their roots against the settings — the file and the environment — rather than scoping them, and why the host still renames the crews it grants no mounts to (`/crews`, `/crews-1`, …). A host that wants its own namespace composes it with `ScopedMountComposition.ForExecution`: entering a scope **replaces** the boot set rather than merging with it, so the composition carries the boot mounts forward and lets the execution's own mounts shadow them at the paths they claim — dropping them takes `/llm-logs` and `/sandbox` down with the run, and takes the root the runner loads the crew from. A folder granted to a crew is an entry of the daemon, readable wherever it lies, without `--allow-external-mounts`. The forge's folders are inputs too: `forge resume` builds its host with the confirmed folders mounted and allowed, and a run about to try the team in its own process refuses, at `folders.confirmed`, an input bound to a directory its validator does not allow (`FORGE-FOLDERS-INVALID`, GAP-27). See [VFS compliance](../architecture/vfs-compliance.md).
- **A tool-call approval in `orkeon-repl` is read between two commands, or by a waiting `runCrew`** — the question a crew asks waits for the read loop, which reads only when no command runs in the foreground, or for a command waiting in `runCrew` (synchronous), which reads the answer itself. Any other command that holds the loop leaves the question waiting until it ends. A command's `ctx.prompt` reading while a question waits takes the operator's line in its place. In the plain console on a terminal, a question written while a line is being edited moves the editor's anchor, as a ticket's completion line already does. The pause of the script's clock while the gate decides holds for the whole engine: every agent of the crew, every run sharing a command file's engine. The REPL registers its approval channel directly (`CompositeLineInterceptor`), without the `SerialisingToolApprovalChannel` decorator the other hosts get: nothing calls the channel concurrently yet, but should two read-class calls of one turn (now run concurrently) both ask, their questions are not queued one at a time. An `act` in `ask` mode with no permission gate fails closed (the call is denied). During a replay (`orkeon-repl --replay`, `/replay`), the next line of the file answers a question the moment it waits: a line written for the next command answers an approval the replay did not expect; one line answers one approval, but a session-wide answer (`s`) also settles every queued approval of the same tool, so the file must carry no line for those; and an approval still waiting when the file ends stops the replay (`replay ended with an approval waiting: <tool>`, exit code `1`). A background instance launched by a `completed()` callback is charged to the replay line in flight when it starts, not to the line that launched its parent. A `human_input` question raises no signal: the replay sees it within a quarter of a second, by looking again.
- **A tool call of a crew agent that the permission gate asks about is refused when the host has no approval channel** — the gate is consulted by `ToolInvocationPipeline` for scripts and YAML crews alike (`permissionMode:` of an agent, else `Orkeon:Security:PermissionGate:DefaultMode`); an `ask` goes to the host's `IToolApprovalChannel`, and with none (the Discord bot) the call is denied and the model reads the reason. With `Orkeon:Checkpointing:Enabled` the question is durable (FWK-23): the daemon and `orkeon run` persist it and stop the run on it (`waiting_for_input`, exit 75) instead of refusing; the Discord bot keeps no path to answer one (a forge session in pause is not a run: it stays at 0).
- **The daemon does not resume a suspended run by itself** — a run whose human-input question outlived `Orkeon:HumanInput:HoldTimeout` (or `Pause: Suspend`) ends `waiting_for_input`; `POST /runs/{id}/input` records the answer and `orkeon run <crew> --resume <id>` resumes it. Each question a parallel task asks is persisted under its own id; the run stops on one of them (the one its exit and `pending_input` show), the others are answered by their `request_id`, and one left unanswered is asked again when the run resumes. A question is replayed at the grain of the task: the task that asked runs again from its start (its tool calls are made again), and the Hierarchical and Autonomous managers' own decisions are not checkpointed.
- **The answer to a human-input question is stored in plaintext** — the checkpoint session keeps the answers (`SessionState.AnsweredInputs`) as they were given, because the resumed task needs them: a store on disk (`json`, `sqlite`) or in Postgres holds them readable, as it holds the task outputs. What is printed or read back of a question - the prompt on the `orkeon run` stderr line and in `GET /runs/{id}` - goes through the masking of the run history (`RedactingRunEventSink.Redact`); the stored prompt is not masked. An answer given without a request id (`--resume <id> --input "..."`, or a `POST /runs/{id}/input` with no `request_id`) goes to the question the run stopped on; with several open and none of them the one it stopped on, it is refused (`409 request_id_required`). A stored tool approval is reused on a resume only for the same tool and the same arguments: another call is asked again.
- **`shell_command`'s confinement: what each backend holds, and where it is checked** — the process is confined by default ([Shell confinement](../architecture/security.md#shell-confinement)): bubblewrap on Linux, Seatbelt on macOS, an AppContainer inside a Job Object on Windows 10 and later; inside a container, or with `Mode = None`, it runs on the host as the host's user and the VFS checks only the paths its command line names. **Where it is checked**: the pure parts (the `bwrap` arguments, the Seatbelt profile, the ACL plan, the Windows command lines, the shell protocol, the choice of `Auto`) are unit tests every CI run executes on Linux; a real `bwrap`, a real `sandbox-exec` and a real AppContainer run only in the nightly `integration.yml` jobs (`ubuntu-latest`, `macos-latest`, `windows-latest`), which fail rather than skip when the backend cannot confine; only the Linux job opens the nightly tracking issue, a red macOS or Windows job shows on the workflow alone. **What a view does not carry**: a sub-path override on a path that does not exist when the session starts (a writable parent lets the process create it; bubblewrap and AppContainer), an internal mount whose folder lies inside an agent-facing mount (reachable through that mount), and a program outside the system directories (`/opt`, a `.dotnet` or `nvm` folder under the home on Linux; `/opt/homebrew` on macOS; anything under the user profile on Windows) until its folder is listed in `Confinement:ReadOnlyPaths`. **An agent root that is a linked git worktree** gets the repository's common dir bound read-only and, over it, its `objects`, `refs`, `logs` and the worktree's own git dir read-write (#188): the agent can rewrite every branch's refs and the shared objects, but not the common dir's `config`, `hooks`, `info`, `modules` or the other worktrees' git dirs, nor any working tree outside its root; a repository without `logs/` cannot record reflogs from the agent; a layout that fails a check (`commondir` or back-link not naming the expected dirs, a symlink on the path) binds nothing; git run on the host inside the agent's worktree still trusts what the agent wrote there, as before, and git run on the host anywhere in the repository follows a link the agent created inside `objects`, `refs` or `logs`; a gitdir written as a virtual path works under bubblewrap only (Seatbelt and AppContainer show the physical paths). **No network** unless `Confinement:AllowNetwork`: a package manager or `git fetch` fails until then. **A timeout returns no partial output** on Linux and macOS (the session is killed before the command's output is read back; Windows returns what was captured), and it resets the session: the next command starts in a new one, without what the previous one left in its `/tmp`. **Windows**: each session grants its mounts by ACE and takes the grant back at its end, and Windows propagates an inheritable ACE to every object below the mount's root, so a session costs one security-descriptor write per file of its mounts, each way (a `node_modules` of 100 000 files is 100 000 writes when the session opens and as many when it closes); the DACL is read, changed and written back, which another process changing the same DACL at that moment can undo. A hidden sub path, or a read-only one inside a writable mount, has its DACL protected for the session and written back as it was at the end (the container's access check skips a deny ACE), so a change another tool makes to that DACL meanwhile is lost. cmd's `dir`, `vol`, `attrib` and `where /r` query the drive's root, which a standard ACL does not open to an AppContainer: they answer "Access is denied." in a confined session. A batch file (`.bat`, `.cmd`, hence `npm.cmd`) is refused in an AppContainer session and runs with `Mode = None` only, and a program is looked up on `PATH` only. **After a host crash**: bubblewrap and the Job Object leave nothing (the kernel kills the tree); under Seatbelt and unconfined on Linux and macOS a watchdog polling every second kills the session's process tree, which a process that left the tree (a double fork) escapes. The scripted runtime ends an agent's scope without awaiting it, so a session's teardown can finish after the agent body returned. On Linux the session's environment keeps the host's `PATH`, with `HOME` and `TMPDIR` on the view's own `/tmp`; Ubuntu 24.04's AppArmor restriction on user namespaces makes `bwrap` fail unless a profile grants it `userns`. **The session bus** reaches a confined session only with `Orkeon:Tools:Shell:Environment:SessionBus = true`, which lets a command leave the sandbox (`systemd-run --user`) and read the keyring; a `unix:abstract=` bus stays reachable under bubblewrap with `AllowNetwork`, since an abstract socket follows the shared network namespace.
- **Per-tool result cut** (RT-10, RT-07) — `Orkeon:Tools:ResultLimits` (`Limits:<tool>`, `MaxParallelToolCalls`, default 4) is bound by `AddOrkeonInfrastructure` and read by the C# agent loops through `ExecutionOrchestrator.ToolLimits`. The scripted `act` reads it too, through `ScriptingHostPorts.ToolLimits`, which `orkeon run`, the runner hosts (`orkeon-host` among them), the REPL's scripting commands and the forge's crew assistant all set; a script host built without that port cuts and fans out with the built-in defaults. The shell default cut went from 4000 to 10000 characters in the pipeline; a result a tool already bounded (`ToolCallResponse.AlreadyBounded`) is not cut a second time. The text-fallback loop (`LegacyTextAgentLoop`) and the dispatcher's text path do not fan out.
- **Agent instances: one memory per agent name** (RT-03, RT-16) — the durable `ctx.memory.agent` store (`FileScriptAgentMemoryStore`) lives under `Orkeon:Scripting:AgentMemory:RootDirectory` (default `/workspace/.orkeon/agent-memory`, see the [configuration reference](./configuration.md#orkeonscriptingagentmemory)); the key is the agent name, so two agents of that name share it. Without a `budget(...)`, `MaxSpawnedAgents` counts per agent run, not per crew run.
- **RAG ingestion lock is in-process** (RT-28, RT-23) — ingests of one collection are serialised by a per-collection `SemaphoreSlim` of the process; two processes sharing a persistent store are not coordinated (a cross-process lock needs provider support). `Prune` removes only the sources of the manifest absent from the requested globs; a failed delete is recorded in the report's errors and keeps its manifest entry. See [RAG pipeline](../architecture/rag-pipeline.md).
- **Markdown in the RaggableTree — no parse validation** (RT-29, RT-40..RT-43) — Edits to a `.md` file (`node_replace`, `node_insert`, `edit_batch`, `ensure_section`, `insert_under_heading`, `replace_mermaid`) are not parse-validated: Markdown has no syntax error to refuse. On an unclosed top-level fence, `replace_mermaid` replaces the body to the end of the file without closing it.
- **Incremental reindex: stated bounds** (RT-30, RT-33) — `incremental_reindex` re-parses the changed files and patches the store per file; calls from unchanged files and Markdown links into a name added or removed by the changed files are relinked without reading the unchanged files. The dirty-set paths do not apply `.gitignore`. A `tests` edge to an overloaded member links every overload (the FQN is name-only). See [RaggableTree](../architecture/raggable-tree.md).
- **Dev-workflow queries: stated bounds** (RT-34, RT-36, RT-37) — `affected_tests` takes `project_depends` from csproj files only, unions `base..HEAD` with the working-tree changes (untracked included), and answers `all` when a project query fills its 1000-row page or an expansion is truncated; symbols below a changed module are read three levels deep. `documents_of` reads a file's sections through a query capped at 1000 sections by the store. `access_cost` counts a write behind `ConfigureAwait` as a read, as `access-cost.py` does.
- **Intent operations — a closed grammar** (RT-42, RT-43) — `ensure_import` does not see a `//` comment inside multi-line import braces (the next binding is hidden), nor `import React, { … }` (default plus named). Structural rewrites and `edit_batch` are best-effort atomic: files are written one by one with a backup or an in-memory original and restored on a failure; if the restore itself fails, the journal is kept and an `AggregateException` is thrown, and the files already written stay changed until the journal is replayed (`structural_rewrite` `$$` in a pattern stays two dollars, one in a fix).
- **Decision tasks run in three processes only.** A task with a `decision:` block or a `when` condition is accepted in Sequential, Parallel and Graph; in Hierarchical, Consensual and Autonomous the load is refused (`DecisionTaskRules.Check`), never ignored, and a crew built in C# that reaches one of them fails before its first task.
- **Decision tasks: what the second iteration leaves out.** No decision node before or after a task (a guard on a task's input or final answer), no go-to outcome, loop or decision journal; no retry (a decision task cannot declare `retry:`, and the graph's own retry loop is gone) and no fallback when a request to the decision model fails (the task fails, the fallback serves an off circuit only); no image and no `box` question in a crew (the `IDecisionModel` port takes both, TypeSafe's opt-in "danger zone" features since Jev 1.13 and 1.14, but a crew's decision task sends text only); the `decision` reranker sends its passages in one request, without batching.
- **A task's `retry:` replays the whole task, and nothing more.** Every mode retries a failed task (`retry: {attempts, backoffMs, backoff}`), tool calls that already succeeded included: no mechanism deduplicates them, and a task whose tools write must be safe to run twice. A failed attempt's tool calls, memory written by tools, metered cost and events stay, and the task callbacks fire once per attempt. A cancellation, a guardian refusal and an exhausted budget are never retried; a timeout and an exhausted failover chain are. There is no scheduler and no message queue: a retry is immediate (or after its backoff), inside the run.
- **The REPL transcript shows no decision detail for crew tasks.** The run's JSONL carries a skipped task's reason and a decision task's answers; the REPL transcript renders no skip reason and no decision label for a crew task.
- **`CrewExecutionEvent` carries part of the decision data.** The in-process event has `Skipped`, `SkipReason` and `Defaulted`, but neither `IsDecision` nor `DecisionAnswers`: those two are on the task snapshot and the `task.completed` event of the JSONL protocol.
- **The YAML `graph:` block runs on the Domain engine only.** A `graph:` outside `process: graph` is refused at load (it used to be accepted without a word), and a handoff between agents is not a graph edge. A `.ork.ts` crew builder has no `graph:` surface: `process("graph")` there runs one node per task, and a graph drawn with `stateGraph(...)` runs on `JsStateGraph` when the script calls `.run()`.
- **`ChatOptionsComposer` translates only part of an agent's `LlmConfig`.** It carries over the model, the sampling and penalty fields, the output cap, the seed, the stop sequences, `Thinking`, the response format and the cache; fields such as `TimeoutSeconds`, `CustomParameters` or `SystemMessage` set on an agent's own `LlmConfig` are not translated into the chat options (the text-fallback loop honours them).
- **Two spellings of the same API-key variable.** Under Linux and macOS, when both `ORKEON_Llm__ApiKey` and `ORKEON_LLM__APIKEY` are set with different values, the run takes either one, and the runtime does not arbitrate between them.
- **Windows: a refused connection may come back slowly (unverified).** The LLM endpoint probe of a run and that of `orkeon doctor` give 2 s each and read a timeout as reachable. If the Windows stack retries the SYN after the reset, as expected, the refusal of an unreachable `localhost` can arrive after the timeout, and the fast failure of `orkeon run` does not trigger. Not observed on Windows yet.
- **Thinking effort is judged against the model on the OpenAI-compatible family only.** The per-model table (`IModelCapabilityRegistry`, `ORKEXP005`) omits an effort a listed model does not take and warns on an unlisted model; the Anthropic and Ollama dialects still judge it by the provider's declared levels (`xhigh` and `max` are sent as they are to a 4.x Claude model that does not know them, which answers with its own error). A model id containing `:` (Ollama's `llama3:8b`) cannot be a key of `Llm:ModelCapabilities`, since .NET configuration has no escape for `:`: key its prefix (`llama3`). The built-in table lists the OpenAI, Gemini and Claude families only: any other model is "unknown" (the effort is sent, with a warning) until `Llm:ModelCapabilities:<id>` declares it. **Haiku 5.5 above 100K prompt tokens** bills more (0.50 / 2.50 $/M); `ModelPricingRegistry` prices the tier up to 100K only, so a long Haiku 5.5 prompt is underestimated and a budget can be exceeded without an alert.
- **`context N%` in the split-pane console reads one call against one setting.** It follows the latest model call of the prompt's turn, so a task launched in that turn shows its own figure until the main command calls again. It is absent for a crew run synchronously through `runCrew`, whose calls no command instance is credited with, and its window comes from `Orkeon:Cli:Session:ContextWindowTokens` alone (`200000` when unset), so it does not follow `/model`.
- **Console palettes are named, not detected.** The palette never comes from the terminal, `ctx.setTheme` lasts for the session, and a selector cannot preview one live: nothing calls a script back from the UI thread.
- **`?` alone cannot start a message on an empty prompt of the split-pane console.** It lists the keys there; while a script's `ctx.prompt` reads, it is text.
- **The prompt recalled on a scrolled transcript hides the row under it.** Scrolling one row further shows that row.
- **Tool-call deltas stop at the sinks that read them.** The reasoning deltas are not forwarded to `ILlmDeltaSink`, and the `mock` provider emits no tool-call delta.
- **Streaming in the split-pane console.** It is on in the REPL and off for a crew run unless `Orkeon:Cli:ConsoleStreaming:Enabled` says otherwise, and an intermediate assistant text does not show in a crew that does not stream. The rows of a table stay hidden until the table ends, and a closing fence adds a blank row.
- **Diffs and code in the split-pane console have no syntax colouring**, which would need a package.
- **A command's wrapped output starts again at column 0.** The next rows of a plain line that wraps do not align under the elbow.
- **Prompts of a split-pane script.** A `ctx.prompt` the script does not await leaves a read open, and the next read of the loop can fail with `A ReadLineAsync is already in progress`. A line typed at the prompt for an approval, buffered and then withdrawn with its question, can reach the loop as a line of its own (rare).
- **The run history of a hosted run is partial.** `orkeon-host` records `run.started`, the task events, `error` and `run.finished` of each run (`Orkeon:RunHistory`, on by default there); the `tool.*`, `llm.call.*` and `cost.updated` events are not published for a hosted run, because the tool, usage and call observers are process-wide services and a daemon runs several crews at once: they stay on `orkeon run --events`. The history of a run keeps no `llm.delta` unless `IncludeDeltas` is set. A run whose host cannot be built (a refused setting, an unreadable crew) leaves no history, and neither does `--resume latest`, whose run the runner names only after looking in the store. The events a run writes before the history can join (`run.started` and what the host build emits) are kept in a buffer of 128; past it they stay on the stream and are not in the history (a warning says how many). A run killed before `run.finished` is `orphaned` only for a reader on the same host: on another host (a shared folder) it stays `running`, and `MaxRuns` and the purge keep counting it as in flight. Two processes may write one history folder: the Sqlite store is in WAL mode with a busy timeout, the JSONL store appends to its index and never rewrites it; a run resumed under its own id (`--resume <id>`) continues the sequence the history holds for it, its second `run.started` carries `resumed: true`, so what `orkeon runs show` prints is no longer line for line the stream of either process. The daemon's own run id is written into `run.started` as `hostRunId`, beside the `ExecutionId` the history is keyed by; the host API unifies the two.
- **`firefox` — stated bounds** (see [the guide](../guides/firefox.md)). The URL policy checks the pages the tab shows, before the browser starts and after every action that may navigate; the sub-resources a page loads (images, scripts, frames, XHR) are fetched by Firefox itself and are not checked — keep the browser on an isolated network when the policy matters. The text of a page is not screened for prompt injection. `search` sends the text of the page's sections to the embedding provider, as one ephemeral collection per page visited (prefix `firefox`), never deleted: the RAG subsystem has no API to drop a collection. The text of `type` is a tool argument the model writes and the transcript keeps: never a secret. One tab is driven at a time — a link that opens a tab moves the session to it, and the tab left behind is read again only after `switch_tab`; the tabs the user or another agent opened in a shared browser are never seen. A named profile is used as it is: the tabs Firefox restores at start are the user's, not the agent's, and what the profile holds (cookies, sessions, extensions) is neither filtered nor removed — an agent on the operator's own profile acts in the operator's name. The lock check before start recognises a profile held by a Firefox of this machine only; one open on another machine through a shared folder is not seen, and Firefox refuses it at start. `screenshot` writes a PNG to a virtual path and returns nothing else: the model does not see the image. A page restored from the history cache (`back`) is recognised by its address: `back` between two history entries of the same address waits for the command timeout (`CommandTimeoutSeconds`, 30 s) before the page is read. Verified on Firefox 159 under Linux; Windows and macOS launch paths are written, not campaigned.
- **`orkeon eval` scores what the suite can score.** `eval run --crew` hands the crew one prompt per case (`task_description`, as the initial context and `{input}`) and scores its final output only: the intermediate task outputs and the events of the run are not in the report. `eval bench` scores recorded outputs and takes no `--crew`; its repeated runs only differ with the LLM judges. `--offline` with `--crew` refuses a crew in which any agent (or the manager) would answer through a provider other than the mock - its own profile, its own provider or the host default - and names the agent and the profile; it does not look at tools that reach the network on their own.
- **`dotnet new` templates: three starting points, no more** (FWK-26) — `Orkeon.Templates` ships `orkeon-host`, `orkeon-plugin` and `orkeon-tool`. The host template runs a `crew.ork.ts` through `ICrewScriptRunner` (so it needs `esbuild` on the machine, and pulls `Orkeon.Tools` and the local embeddings through `Orkeon.Scripting`); it is shaped like the `orkeon-host` daemon (generic host, `appsettings.json`) but is not the daemon: no crew registry, no chat gateway, no channels. The plugin template references `Orkeon` at compile time only (`ExcludeAssets="runtime"`) and starts with the manifest of the sample plugin; a plugin is loaded from a folder, nothing publishes it. Every generated project pins the Orkeon packages to the version the template package was packed at, so a template installed from an older package generates a project on that older line. Hot reload and an IDE extension are not part of it.
- **The permission gate decides after a script's tool hooks** (FWK-06). A script's `onToolCall` callback runs before the gate, which judges the input it returns (one consultation per call, inside the invocation with the tool-invocation pipeline): a call the gate denies has still run the callback. The tool budget is charged only once the guardian and the gate admit the call.
- **A bounded read of a JSONL run history reads the whole file.** `IRunHistoryReader.ReadEventsAsync(runId, fromSeq, limit, ct)` applies the limit in SQL on the Sqlite store; the JSONL store reads the run's file and stops after the limit.
