# Référence du CLI `orkeon`

L'outil en ligne de commande `orkeon` est le point d'entrée principal du framework : il exécute les crews YAML et les scripts TypeScript (`.ork.ts`), transforme un besoin en langage courant en crew (l'Atelier), génère une configuration, sonde les fournisseurs LLM, pilote le sous-système RAG, cherche dans les cas d'usage d'exemple, connecte des comptes e-mail, écrit les typings d'éditeur du DSL de scripting, sert ses outils à un client MCP et diagnostique une installation. Il est construit depuis `src/scripting/Orkeon.Scripting.Cli` et se packe comme dotnet tool `orkeon` :

```bash
dotnet tool install --global Orkeon.Scripting.Cli --prerelease
orkeon doctor
```

Les binaires de release et les installeurs (zip/MSI Windows, paquet Debian, tarballs macOS) embarquent le même CLI, autonome — aucun SDK .NET requis. Voir [Trois façons d'exécuter Orkeon](../getting-started/three-ways-to-run-orkeon.md).

Mettez le tool à jour avec `dotnet tool update --global Orkeon.Scripting.Cli --prerelease`. La mise à jour de tous les autres canaux, et le suivi de `main` entre deux releases : [Mettre à jour Orkeon](../getting-started/three-ways-to-run-orkeon.md#mettre-à-jour-orkeon).

**Codes de sortie** (stables) : `0` OK · `1` erreur de script/config (fichier manquant, script invalide, échec de validation) · `2` le run a échoué — une erreur runtime inattendue, un service que le host n'a pas pu construire au démarrage, ou une équipe qui a tourné sans réussir (une tâche sans réponse finale, un disjoncteur déclenché, un consensus non atteint) · `130` annulé par Ctrl+C. Sur un code `2`, la **dernière ligne de stderr** est `ERROR: <raison>` — la phrase qui dit pourquoi ; le type de l'exception et sa trace de pile ne sont journalisés qu'en `--verbose 2` (ou `ORKEON_DEBUG=1`).

**La ligne de commande.** `orkeon`, `orkeon --help`, `orkeon -h` et `orkeon help` impriment la liste des commandes et sortent avec `0` ; `orkeon <commande> --help` imprime les options d'une commande. `orkeon --version` (ou `orkeon version`) imprime `orkeon <version>` — `-v` n'est pas la version, c'est `--verbose`. Les commandes sont `run`, `init`, `doctor`, `llm`, `rag`, `forge`, `usecases`, `email`, `typings` et `mcp`, reconnues avant toute autre chose. Le verbe `run` est facultatif : un premier argument qui commence par `-`, ou qui se lit comme une crew — il contient un `/` ou un `\`, se termine par `.ork.ts`, `.ork.js`, `.ts`, `.js`, `.yaml` ou `.yml`, ou nomme un fichier ou un dossier existant — est confié à `orkeon run`. Tout autre mot est refusé avec `orkeon: unknown command '<mot>'` et le code `1`.

## `orkeon run`

```bash
orkeon run <crew.ork.ts | crew.yaml | répertoire-crew/> [options]
```

Exécute une définition de crew et imprime son résultat sur stdout. Le dispatch dépend de la cible : `.yaml`/`.yml` — ou un répertoire contenant un crew YAML multi-fichiers (`config.yaml` + `agents/` + `tasks/`, ou le triplet plat `crew.yaml`/`agents.yaml`/`tasks.yaml`) — part vers le runner one-shot partagé, qui imprime la sortie de la crew sous une bannière `=== Crew Output ===`. Tout autre fichier est un script (`.ork.ts`, `.ts`, `.js`), assemblé par esbuild et exécuté par Jint, et c'est sa source qui choisit le moteur ([les deux formes](./scripting-dsl.md#les-deux-formes)) : un script qui affecte `globalThis.crew` est une définition de crew **déclarative** et part vers le même runner partagé que le YAML (tâches, process et manager honorés) ; tout autre script est **procédural** — l'hôte de scripting l'exécute et imprime son résultat en JSON. `--validate` et `--list-tools` passent toujours par le runner partagé.

| Option | Description |
|---|---|
| `-s, --settings <chemin>` | Chemin vers `appsettings.json`. Sans elle, une chaîne de repli s'applique (ci-dessous). |
| `-m, --mount <spec>` | Montage VFS, format Docker `<physique>:<virtuel>:<droits>[;sous-chemin:droits]`. Plusieurs montages se passent **séparés par des espaces derrière un seul flag** (`--mount a:/x:ro b:/y:rw`) — le parseur rejette un `--mount` répété. Une lettre de lecteur Windows ne demande rien de particulier (`C:\src:/workspace:ro`) ; un chemin que la forme nue ne peut pas porter — contenant un `:` ou un `;`, ou finissant par une barre oblique inverse — se met **entre guillemets** : `"/data/odd:name":/data:ro`, `"C:\src\":/workspace:ro`. Ces guillemets appartiennent à la grammaire des *montages*, donc votre shell ne doit pas les manger : en bash/zsh, entourez toute la spec de guillemets simples (`--mount '"/data/odd:name":/data:ro'`) ; en PowerShell, doublez-les (`--mount '""/data/odd:name"":/data:ro'`). La barre oblique inverse n'est jamais un caractère d'échappement. Le chemin virtuel est toujours un nom commençant par `/` — jamais un chemin disque ([ADR-008](../adr/ADR-008-virtual-paths-are-the-only-currency.md)), et `/crew`, `/script`, `/llm-logs`, `/sandbox` et `/credentials` sont réservés par le runner (`RunnerVirtualRoots.All`) : un mount qui en revendique un est refusé avec le code 1, et refusé de la même façon qu'il ait été écrit ici ou déclaré dans le fichier de settings — le garde lit les deux, et nomme les racines que *cette* commande réserve plutôt qu'une liste figée. `/credentials` est réservée par toutes les commandes : le runner y garde les jetons OAuth des comptes e-mail ([`orkeon email`](#orkeon-email)). `orkeon forge` ne réserve que `/sandbox` : il n'accepte aucun `--mount`, monte lui-même `/workspace`, `/forge` et `/output`, et place ces trois racines face aux settings exactement comme un `--mount` l'est (phrase suivante) — une entrée des settings sur l'une d'elles est remplacée pour l'essai, si bien qu'un fichier de settings nommant `/output`, mount ordinaire d'un run normal et nom que Studio donne au dossier d'écriture d'une équipe, forge sans rien changer. **Face au fichier de settings, un `--mount` est placé par racine virtuelle** : sur une racine que `Orkeon:FileSystem:Mounts` déclare déjà (fichier de settings ou environnement `ORKEON_`), le `--mount` **remplace toutes les entrées des settings de cette racine pour ce run** — il est écrit à l'index de la première entrée, les autres sont retirées, et le journal dit `mount /x: --mount replaces the settings entry` ; sur une racine neuve, il est **ajouté** après toutes les entrées déclarées. Les entrées des settings qu'aucun `--mount` ne nomme restent en vigueur. Une racine n'est en double que lorsqu'une même *source* la revendique deux fois sans que rien ne distingue les revendications : deux `--mount` sur la même racine (`--mount a:/x:ro b:/x:rw`), ou un fichier de settings qui déclare deux fois une racine avec une entrée sans identifiant (ligne suivante), sont refusés avec le code 1 et une seule ligne (`ERROR: '/x' is mounted twice on the command line: … Keep one.` / `… declared twice in <settings> (…) and '<entrée>' has no id. Give every entry an id …`), avant qu'aucun host ne soit construit. |
| `--mount-id <ulid>` | Sélectionne, parmi plusieurs entrées des settings déclarant **une même racine virtuelle**, celle que ce run garde (VFS-90). Une entrée des settings peut porter un identifiant — l'ULID de 26 caractères devant son `|`, `01J9Z3K4M5N6P7Q8R9S0T1V2W3|C:\data:/output:rw` ; Orkeon Studio en écrit un à chaque enregistrement — et deux entrées ne partagent une racine que si toutes deux en portent un. Plusieurs identifiants se passent **séparés par des espaces derrière un seul flag**, comme `--mount`. L'entrée désignée est gardée telle que déclarée (dossier, droits) ; les autres entrées de sa racine sont **retirées pour le run** — pas montées, pas en liste blanche, leur dossier pas sondé. Sans l'option, le bloc `mounts:` de la crew (`<ulid>|/output`, voir le [schéma YAML](../architecture/yaml-schema.md)) sélectionne de la même façon ; sans l'un ni l'autre, une racine déclarée plusieurs fois est refusée avec le code 1 et une ligne qui nomme chaque identifiant (`ERROR: '/output' is declared twice in <settings> (<idA>: <dossierA>, <idB>: <dossierB>) and nothing selects one. Pass --mount-id <id>, list '<id>|/output' under mounts: in the crew, or pass --mount <folder>:/output:rw to replace them all.`). Un identifiant qu'aucune entrée ne porte, ou mal formé, est refusé de même ; un `--mount` sur la même racine l'emporte sur l'option, avec une ligne `WARNING:` ; une racine que la crew exige et que rien ne fournit est refusée aussi (`the crew requires '/output' … pass --mount <folder>:/output:rw`). Les agents ne voient jamais un identifiant : `list_mounts` et les messages de refus d'accès ne nomment que des chemins virtuels. |
| `--allow-external-mounts` | Autorise les arguments `--mount` hors du répertoire de travail (ou `ORKEON_ALLOW_EXTERNAL_MOUNTS=1`) : le chemin de base de chaque `--mount` est ajouté à la liste blanche `PathSecurity:AdditionalAllowedDirectories` contre laquelle `PathValidator` vérifie les chemins résolus, à la suite de ce que les settings y listent déjà. Un montage **déclaré dans le fichier de settings** (ou via des variables `ORKEON_`) n'a besoin d'aucun drapeau : son chemin de base est toujours mis en liste blanche, parce qu'un dossier déclaré est l'intention explicite du propriétaire de la machine — jusque-là un tel dossier était monté et chaque accès refusé comme « outside the allowed workspace directory », sans qu'aucun drapeau puisse y remédier. |
| `-v, --verbose <0-2>` | `0` silencieux, `1` échanges LLM & outils, `2` debug complet. |
| `--llm-log` / `--llm-log-path <rép>` | Journalise les échanges LLM complets en JSONL (répertoire par défaut `./llm-logs`) ; `--llm-log-path` implique `--llm-log`. |
| `--inputs <json>` / `--inputs-file <chemin>` | Entrées structurées pour un **script procédural** (la globale `inputs`). Un script déclaratif ou un crew YAML les ignore — un script déclaratif le signale sur stderr. |
| `-V, --var CLE=VALEUR` | Variable pour le `CrewInput` d'un **crew YAML** (gabarits de tâche `{CLE}`). Plusieurs variables séparées par des espaces derrière un seul `-V` (un flag répété est rejeté). |
| `--initial-context <texte>` | Contexte initial passé au `CrewInput` d'un **crew YAML**. |
| `--memory-limit-mb <n>` | Plafond mémoire Jint d'un script procédural (`0` le désactive). Par défaut : `Orkeon:Scripting:Limits:MemoryLimitBytes`, 100 Mo. |
| `--validate` | Dry run : résout les settings, construit l'hôte, charge le crew avec résolution stricte des outils — aucun appel LLM, aucun kickoff. Imprime `VALIDATION OK/FAILED: …`. |
| `--list-tools` | Construit l'hôte, imprime le registre trié des outils runtime, puis sort. Aucun chemin de crew requis. |
| `--events jsonl` | Émet le protocole d'événements versionné sur stdout au lieu du rendu texte, et lit des commandes sur stdin. C'est ainsi qu'Orkeon Studio observe un run. Voir [Le bus d'événements du run](../architecture/run-event-bus.md). `jsonl` est la seule valeur ; toute autre est refusée avec le code 1. |
| `--stream` | Avec `--events`, émet aussi les `llm.delta` jeton par jeton. Verbeux par nature : désactivé sauf demande. |
| `--client <nom>` | Avec `--events`, le nom auquel le processus observateur répond sur le hub du run (`client://<nom>`, défaut `studio`). Les agents peuvent lui écrire à cette adresse ; le bloc `links:` d'une crew l'autorise. Un nom vide ou contenant un `/` est refusé avec le code 1 ; sans `--events`, l'option est sans effet, et un avertissement le dit. |

```bash
orkeon run examples/01-enterprise/01-research-assistant/config.yaml \
  --settings examples/appsettings/appsettings.deepseek.local.json \
  --mount ./out:/output:rw -v 1
```

**Résolution des settings** — sans `--settings`, le CLI suit une chaîne de repli : `appsettings.json` à côté du fichier de crew, puis un `appsettings/appsettings.json` trouvé en remontant les répertoires parents, puis le fichier global par utilisateur écrit par `orkeon init`, puis les variables d'environnement `ORKEON_*` seules. Un `--settings` explicite qui nomme un fichier inexistant arrête la chaîne là — une ligne `WARNING:`, puis les variables d'environnement seules — au lieu de passer à l'emplacement suivant. Détails et matrice de profils prêts à l'emploi : [Exécuter votre premier exemple](../getting-started/run-your-first-example.md).

## `orkeon forge`

```bash
orkeon forge "résumer chaque matin les nouvelles offres de mon fournisseur"   # partir d'un besoin
orkeon forge "trier mes e-mails par urgence" --reference 03-email-pipeline   # partir d'un besoin, sur le modèle d'un cas d'usage
orkeon forge                                   # ouvrir sur l'entretien
orkeon forge list                              # lister les sessions du workspace
orkeon forge resume <slug>                     # reprendre une session exactement là où elle s'est arrêtée
orkeon forge resume <slug> --read <dir>        # l'essayer sur les documents de <dir>
orkeon forge resume <slug> --adopt             # garder l'équipe telle quelle, sans essai
orkeon forge promote <slug> --to <dir> --name <équipe>   # sortir une session prête en dossier ordinaire, au nom de l'équipe
orkeon forge reopen <dossier-equipe>           # retrouver — ou reconstruire depuis crew/ — la session liée à une équipe promue
orkeon forge schedule <dossier-equipe>         # installer la planification de l'équipe dans le planificateur du système
orkeon forge schedule <dossier-equipe> --check # dire si elle est installée, absente ou à réinstaller
orkeon forge unschedule <dossier-equipe>       # la retirer, avec schedule/ et l'enregistrement de forge.json
orkeon forge rename <dossier-equipe> --name <nom>   # renommer l'équipe : dossier, session, titres, planification — tout ou rien
```

L'Atelier : un parcours guidé du besoin en langage naturel à l'équipe déployable. Un assistant vous interroge et capte un brief structuré — objectif, entrées, **critères d'acceptation**, un exemple d'entrée — puis propose un plan d'équipe, le rend, le valide, **l'essaie en bac à sable sur votre exemple**, et juge le résultat **contre vos propres critères**. Non conforme ? Le diagnostic alimente une boucle de correction, bornée par un budget dur (itérations, jetons, temps). Chaque session vit sous `.orkeon/forge/<slug>/` — reprenable, diffable entre tentatives, auditable.

**L'étape des dossiers.** Entre le brief et le plan, la forge fixe les dossiers de l'équipe. L'assistant liste dans le brief (`folders` : `path`, `role` `input`|`output`, `purpose`) chaque dossier que le besoin nomme — « …des PDF dans `/inpdf`, le Markdown dans `/outmd` » — et, s'il n'en nomme aucun, la forge propose `/workspace` à lire (seulement si quelque chose entre) et `/output` où écrire. Un dossier est un seul segment absolu de lettres, chiffres, `-`, `_` ou `.` ; `/forge` et les racines propres au moteur sont refusés, et au moins un dossier doit être une sortie. La forge émet alors `folders.proposed` (`folders`) et attend `folders.confirmed` sur stdin (`{"kind":"folders.confirmed","folders":[{"path","role","purpose","dir"}]}` — la proposition telle quelle ou modifiée, `dir` le dossier réel relié à un dossier, absent pour un dossier gardé dans l'équipe). Une liste qui enfreint les règles, ou relie un dossier qui n'existe pas, est un `FORGE-FOLDERS-INVALID` récupérable, et les dossiers sont proposés à nouveau. De même, quand le run essaie l'équipe dans ce même processus (sans `--dry`), d'un dossier d'entrée relié à un dossier réel que les outils fichiers du run n'autorisent pas — un dossier hors du répertoire de travail : ces outils gardent les dossiers avec lesquels ils ont démarré, si bien que le dossier serait monté pour l'essai puis refusé à chaque lecture. Le message dit le chemin qui marche, celui de Studio : confirmer les dossiers dans un run qui s'arrête avant son essai (`orkeon forge resume <slug> --dry`), puis `orkeon forge resume <slug>`, dont l'hôte les monte et les autorise dès son démarrage. Dans le terminal, et avec `--auto`, la proposition est acceptée telle quelle et affichée. La liste confirmée est gardée dans le `folders.json` de la session (avec les dossiers réels) et dans le brief (sans eux — un chemin physique n'atteint jamais un prompt), annoncée par `brief.ready`, et sert partout ensuite : les livrables du plan doivent tomber dans un dossier de sortie confirmé (`FORGE-BLUEPRINT-INVALID` / réparation sinon), le bloc `mounts:` de l'équipe nomme la liste, l'essai la monte, la promotion la porte. Une session arrêtée à cette question la repose à la reprise, sans nouvel entretien.

Démarrer ou reprendre un cycle exige un LLM configuré (`orkeon init`) : la forge refuse d'ouvrir l'entretien sans lui (`FORGE-LLM-UNAVAILABLE`) plutôt que de dégrader en silence. `list`, `promote`, `reopen`, `schedule`, `unschedule` et `rename` sont entièrement hors ligne.

`reopen <dossier-equipe>` rend une équipe promue à nouveau modifiable, quoi qu'il soit advenu de sa session. Une seule règle décide de la session à laquelle un dossier est lié (la règle R) : chaque session porte un identifiant stable — annoncé par `session.started` — que sa promotion recopie dans le `forge.json` du dossier, et la session qui porte cet identifiant est liée quand son `promotedTo` nomme le dossier, ou quand le dossier qu'il nomme a disparu ou ne porte plus l'identifiant : l'équipe a été déplacée ou renommée, et la session est pointée vers sa nouvelle place. Quand `promotedTo` nomme un autre dossier existant qui porte le même identifiant, ce dossier-ci est une **copie**, liée à rien ; un dossier sans identifiant, ou avec un identifiant qu'aucune session ne porte, n'est lié à rien non plus. Une session liée est seulement nommée : reprenez-la. Sinon — session supprimée, dossier forgé sur une autre machine ou importé, copie, dossier sans identifiant — une session est **reconstruite** depuis le dossier lui-même : le plan est relu depuis `crew/` (`config.yaml` + `agents/` + `tasks/` par entité, ou un seul `crew.yaml`), le brief vient du `forge.json` que chaque promotion écrit à côté de `FORGE.md` — ou est dérivé du plan, et la commande le dit — et le crew est copié tel quel. La session reconstruite reçoit un nouvel identifiant, écrit dans le `forge.json` du dossier (créé sans brief quand le dossier n'en avait pas ; celui d'une copie est réécrit, si bien qu'elle ne peut plus atteindre la session de l'original, et sa session porte le nom du dossier de la copie), et se pose à la pause `--dry`, en pointant vers le dossier : le `reopen` suivant la retrouve, `resume --edit --dry`, `resume`, `resume --adopt` suivent comme d'habitude, et un `promote --to` vers le même dossier le met à jour en place. Un dossier sans crew YAML (crew script, disposition étrangère, fichiers qui ne décrivent pas un plan valide) est refusé avec `FORGE-TEAM-UNREADABLE` et les raisons ; le verbe n'accepte aucune option sauf `--events`. C'est ainsi que fonctionne le « Modifier » d'Orkeon Studio, sur toute équipe.

| Option | Description |
|---|---|
| `--format yaml\|script` | Format rendu (défaut `yaml`). `script` rend un `crew.ork.ts` éditable et exige esbuild — absent, une nouvelle session retombe sur YAML avec `FORGE-ESBUILD-MISSING`. Le format d'une session ne change jamais en reprise. |
| `--events jsonl` | Émet le protocole d'événements versionné sur stdout au lieu du rendu terminal ; les réponses descendent sur stdin (c'est ainsi qu'Orkeon Studio pilote la forge). La valeur est facultative : l'argument suivant n'est pris pour elle que s'il vaut `jsonl`, tout autre mot reste dans le besoin (`orkeon forge --events veille des prix` forge « veille des prix »). |
| `--auto` | Arbitre les verdicts non conformes sans humain, dans les limites du budget. |
| `--dry` | S'arrête après la validation — génère et valide, n'exécute jamais. Reprenez sans `--dry` pour essayer. |
| `--edit` | *(resume)* Amende le blueprint d'une session en pause avant son essai : le JSON amendé passe par le canal (`blueprint.edited` sur stdin en mode `--events`, une ligne collée dans le terminal), est validé intégralement, puis re-rendu de façon déterministe — zéro token LLM, même itération, mais un LLM configuré reste exigé (`FORGE-LLM-UNAVAILABLE` sinon). Avec `--dry`, la session se remet en pause à la même frontière. Sur une session qui n'est pas en pause avant son essai, il sort en 1 avec un message, sans événement. À l'arbitrage, utilisez plutôt la décision `edit`. |
| `--adopt` | *(resume)* Garde l'équipe telle qu'elle a été générée, sans essai : une session mise en pause par `--dry` passe directement à Ready. Entièrement hors ligne — pas d'hôte, pas de LLM, pas de dossier d'exécution, zéro jeton. Ce qui est sauté, ce sont les **preuves** que produit un essai, jamais un contrôle : à cette pause le crew est rendu et validé, et la promotion n'a jamais consommé d'artefact d'essai (`verdict.json` est facultatif et `FORGE.md` écrit « aucun verdict enregistré »). `resume --adopt` sur une session qui n'est pas à cette pause est refusé avec `FORGE-INVALID-STATE` ; `--adopt` hors de `resume`, ou avec `--edit`, est une erreur d'usage (code 1). Les options de cycle (`--read`, `--auto`, `--dry`, `--pack`, `--max-*`, `--settings`) sont sans effet sur une adoption. |
| `--max-iterations <n>` / `--max-tokens <n>` / `--max-seconds <n>` | Le budget (défaut 3 itérations, au moins 1 ; jetons et secondes valent `0` par défaut = illimité, une valeur négative est refusée). Une reprise peut le relever ; la consommation est toujours reportée. |
| `--settings <chemin>` | Mêmes sémantiques qu'`orkeon run`, ancrées au répertoire de travail — **forme longue uniquement** : le parseur du forge est artisanal et ne définit aucun alias court, ni `--help` (une option inconnue, `--help` compris, est refusée avec le code 1). |
| `--read <dir>` | *(nouvelle session, resume)* Le dossier que l'essai lit derrière le premier dossier d'entrée que la liste confirmée ne relie à aucun dossier réel (`/workspace` quand le besoin n'a nommé aucun dossier), à la place du répertoire de travail. Le répertoire de travail garde tous ses autres rôles — la session vit toujours sous son `.orkeon/forge/<slug>/`, les settings se résolvent toujours à côté : `--read` déplace les documents, pas l'atelier. Un dossier inexistant est refusé avec le code 1 avant toute création de session (`--read names no directory`) ; `promote` refuse l'option, puisqu'il ne monte rien. Un dossier de lecture hors du répertoire de travail est automatiquement mis en liste blanche pour les outils fichiers, comme `orkeon run` le fait pour le dossier de son script — les montages du forge sont les siens, il n'y a donc pas de `--allow-external-mounts` ici — et il en va de même d'un dossier réel relié à un dossier que la session avait confirmé quand le run a démarré (une reprise ; voir l'étape des dossiers pour un dossier confirmé pendant le run). C'est ainsi qu'Orkeon Studio réessaie une équipe rouverte sur son propre dossier d'entrée. |
| `--reference <id>` | *(nouvelle session)* Le cas d'usage qui sert de modèle à l'équipe : un identifiant d'[`orkeon usecases`](#orkeon-usecases), dont le crew — agents, tâches, processus, outils de chaque agent — est montré à l'assistant qui conçoit l'équipe comme un modèle de **structure, pas de contenu à recopier** : le brief seul décide de ce que fait l'équipe. Montré quand l'équipe est conçue, jamais pendant l'entretien ; les outils que le catalogue du bac à sable n'offre pas en sont retirés, et sa taille est bornée — chaque texte coupé à 200 caractères, l'ensemble à 4 000 (environ 1 150 jetons), au-delà desquels la suite d'une équipe plus grande est coupée, et c'est dit. Mesuré le 2026-09-24 sur le vrai catalogue d'outils : une référence ajoute de 2 100 à 4 500 caractères à chaque appel qui conçoit l'équipe — +590 à +1 290 jetons estimés, +800 pour le cas d'usage médian, sur un appel d'environ 3 000 sans elle. La session l'enregistre (`reference` dans `session.json` : identifiant et titre) et l'annonce dans `session.started` ; une reprise ou une réouverture compose à nouveau avec elle, et l'option est refusée ailleurs que sur une nouvelle session. La promotion la trace : « Inspiré de : `<titre>` (`<id>`) » dans `FORGE.md`, à côté de la ligne de provenance (« Inspired by: » quand le brief n'est pas en français), et `reference` dans `forge.json`. Un identifiant inconnu est refusé avec le code 1 et `USECASES-UNKNOWN-ID` avant toute création de session et tout appel de modèle — une ligne `error` puis `session.finished` « failed » en mode `--events`. C'est ainsi qu'Orkeon Studio transmet le cas d'usage choisi dans la galerie de l'assistant. |
| `--pack <dir>` | Surcharge le pack de prompts embarqué. |
| `--to <dir>` | *(promote)* Dossier de destination ; doit être inexistant ou vide — sauf s'il s'agit du dossier auquel la session est liée (celui vers lequel elle a promu, ou ce dossier déplacé ou renommé depuis ; jamais une copie, refusée avec la raison), qui est alors mis à jour en place. |
| `--name <équipe>` | *(promote, rename)* Le nom de l'équipe : il devient le titre de `FORGE.md`, de `forge.json` et de la session elle-même — sans lui, ils gardent l'objectif du brief ; pour `rename`, le nouveau nom, qui nomme aussi le dossier (ci-dessous). Pris tel qu'écrit, tiret initial compris : la valeur de `--name` n'est jamais lue comme l'option suivante. Orkeon Studio le transmet toujours. |
| `--schedule daily@HH:mm\|hourly` | *(promote)* Génère les artefacts de planification sous `schedule/` — XML de tâche Windows, timer systemd, ligne cron — et note la planification dans `forge.json`. La promotion elle-même n'installe rien : c'est `forge schedule` (ci-dessous). |
| `--check` | *(schedule)* Dit où en est la planification — `installed`, `absent` ou `stale` — sans rien changer. |
| `--with-settings` | *(promote)* Copie le fichier de settings résolu dans le dossier. Off par défaut — un settings porte souvent des clés API et le dossier est fait pour être partagé. |

Le bac à sable : l'essai tourne in-process avec les dossiers confirmés montés et rien d'autre de l'équipe — `/workspace` et `/output` seulement quand la liste les contient. Les écritures sont confinées au dossier de la session : chaque dossier de sortie atterrit dans `folders/<nom>` et est mis de côté dans `runs/<n>/folders/<nom>` après l'essai, là où la vérification des livrables regarde ; `/forge` contient ses fichiers de travail. Un dossier d'entrée lit le dossier réel qui lui est relié, sinon `--read`, sinon le répertoire de travail pour `/workspace`, sinon le `folders/<nom>` de la session — un dossier gardé dans l'équipe, lisible avant que l'équipe existe. `shell_command`/`code_interpreter` sont retirés du catalogue d'outils — le plan d'équipe ne peut nommer que des outils que la validation acceptera.

Le dossier promu est ordinaire : `crew/` (ou `crew/crew.ork.ts`), un dossier par dossier confirmé (`/workspace` lit `input/`) — ce que la session gardait dans son `folders/<nom>` y est déplacé —, `run.sh`/`run.cmd` composés contre la grammaire d'`orkeon run` avec ces dossiers montés et vos entrées d'exemple pré-remplies, `FORGE.md` — la carte d'identité de l'équipe (objectif, critères d'acceptation, verdict, version), écrite en français quand le brief est en français, et en anglais pour toute autre langue — et `forge.json`, son jumeau lisible par la machine (identifiant de la session, slug, titre, format, instant de promotion, brief, et le cas d'usage qui lui a servi de modèle) que `forge reopen` lit — l'identifiant est ce qui relie le dossier à sa session où qu'aille le dossier. `orkeon run <dir>/crew` le lance — depuis l'intérieur de `<dir>`, et sans les `--mount` que fournit `run.sh`, si bien qu'une équipe qui produit des livrables n'écrit rien par cette voie ; le lanceur Studio détecte le dossier et pose les montages lui-même.

Une fois la promotion écrite, la session suit son équipe : son dossier sous `.orkeon/forge/` prend le nom du dossier de destination, tel quel — suffixé `-2`, `-3`… quand une autre session porte déjà ce nom, qui n'est jamais écrasée — et `session.json` comme `forge.json` prennent le nouveau slug : `forge list` montre chaque session adoptée sous le nom de l'équipe qu'elle a produite, plus sous le besoin avec lequel elle a été ouverte. `--events` l'annonce : `session.renamed` porte `from`, `to`, le nouveau `dir` et `suffixed`. Un renommage que le disque refuse (poignée ouverte sous Windows, antivirus) laisse la promotion réussie — code 0 — avec un événement `warning` (`FORGE-SESSION-NOT-RENAMED`) : l'équipe reste liée à sa session par l'identifiant, dans tous les cas. Les artefacts générés portent eux aussi le nom du dossier d'équipe, jamais celui de la session : `schedule/orkeon-<équipe>.service` et `.timer` avec leurs descriptions, la tâche planifiée `Orkeon <équipe>`, la commande d'installation, l'en-tête des lanceurs. `<équipe>` est le nom du dossier tel que l'écrit la règle des dossiers — ASCII minuscule et tirets, ce qu'un nom d'unité accepte — c'est-à-dire le nom lui-même pour tout dossier que crée Studio.

**La planification.** Orkeon n'a pas d'ordonnanceur à lui : c'est le système qui lance une équipe planifiée, et le CLI — qui possède les artefacts — l'y installe et l'en retire. `promote --schedule` génère `schedule/` (les trois familles, quelle que soit la machine) et note la planification déclarée dans `forge.json` ; il ne touche jamais au planificateur du système. `forge schedule <dossier-equipe>` l'enregistre pour l'utilisateur courant, sans élévation ni mot de passe :

- **Windows** — `schtasks /Create /TN "Orkeon <équipe>" /XML schedule/windows-task.xml /F`. La tâche s'exécute tant que l'utilisateur a sa session ouverte ; une exécution manquée machine éteinte ou sur batterie a lieu dès que possible.
- **Linux** — les deux unités sont copiées dans `~/.config/systemd/user/` (`$XDG_CONFIG_HOME` respecté), puis `systemctl --user daemon-reload` et `enable --now orkeon-<équipe>.timer`. Un timer utilisateur tourne tant que l'instance systemd de l'utilisateur tourne — de l'ouverture à la fermeture de session, ou toujours une fois `loginctl enable-linger` posé.
- **macOS et les autres systèmes** — une ligne de la crontab de l'utilisateur, marquée `# orkeon:<équipe>`, lue avec `crontab -l` et réécrite en entier avec `crontab -` : toutes les autres lignes restent exactement telles quelles, et rien n'est jamais écrit par-dessus une crontab qui n'a pas pu être lue. launchd n'est pas utilisé.

Chaque commande est un programme et sa liste d'arguments, jamais un shell. Installer à nouveau réinstalle. Des artefacts qui décrivent un autre dossier — une copie, une équipe déplacée ou renommée depuis sa promotion — sont d'abord régénérés, et un enregistrement que ce dossier a fait sous un ancien nom est retiré. Ce qui a été installé est noté dans `forge.json` (`schedule.installed` : expression, famille, noms, dossier, date) ; le contrôle et le retrait agissent sur ces noms notés, jamais sur des noms qu'ils calculeraient. `--check` ne change rien et répond `installed`, `absent` (jamais installée, retirée hors d'Orkeon, faite sur un autre système — ou le dossier est une copie, et l'enregistrement noté est celui de l'original) ou `stale`, à réinstaller (elle lance un autre chemin, porte un autre nom, se déclenche sur une autre planification que celle déclarée, ou est désactivée). `forge unschedule <dossier-equipe>` retire l'enregistrement de ce dossier, `schedule/` et l'enregistrement de `forge.json` ; rien à retirer est un succès, et une copie ne retire jamais l'enregistrement de son original. Un nom qu'un autre dossier d'équipe tient déjà n'est jamais remplacé (`FORGE-SCHEDULE-NAME-TAKEN`) ; un dossier qui ne déclare aucune planification n'a rien à installer (`FORGE-SCHEDULE-NONE`). Quand le système refuse — une stratégie, pas de bus de session utilisateur, pas de `crontab` — le verbe sort en 1 avec `FORGE-SCHEDULE-REFUSED`, et l'événement `error` porte `command` : ce qu'il faut lancer à la main à la place. Avec `--events`, l'issue est un événement `schedule.state` (`path`, `state`, `reason`, `expression`, `family`, `names`, et `removed` pour un retrait). Une ré-adoption qui abandonne la planification laisse l'enregistrement tourner et le dit par un `warning` (`FORGE-SCHEDULE-STILL-INSTALLED`) : seul `unschedule` le retire. Les deux verbes ne prennent aucune option hors `--events` (et `--check` pour `schedule`). Les lanceurs appellent `orkeon` par son nom, et cron comme systemd donnent à une exécution planifiée un `PATH` minimal : un CLI installé par `dotnet tool install` (sous `~/.dotnet/tools`) n'y est pas trouvé, le `/usr/bin/orkeon` du paquet `.deb` l'est. La clé suit le même contrat : une exécution planifiée ne lit ni le `PATH` ni les `export` du profil du shell, si bien que la variable que le fichier de réglages nomme pour une clé (`ApiKeyEnvVar`, p. ex. `ZAI_API_KEY` — voir la [configuration](./configuration.md#la-clé-dapi-apikey-apikeyenvvar)) va là où le planificateur lit : une ligne `ZAI_API_KEY=…` dans `~/.config/environment.d/*.conf` pour le gestionnaire systemd de l'utilisateur, une ligne de variable en tête de la crontab pour cron — des fichiers que l'utilisateur possède et écrit lui-même ; Orkeon n'en écrit aucun. Sous Windows, la tâche tourne comme l'utilisateur, et un run lit la portée Utilisateur où Orkeon Studio mémorise les clés, quel que soit l'environnement que construit le Planificateur de tâches. C'est ainsi qu'Orkeon Studio installe, contrôle et arrête la planification d'une équipe.

**Renommer une équipe.** `forge rename <dossier-equipe> --name <nom>` renomme une équipe promue, tout ou rien. Le dossier prend le dossier du nom, à côté de là où il est — la règle des dossiers, `equipe` quand il ne reste rien d'utilisable ; la session que la règle R lie au dossier le suit, comme après une promotion (suffixée `-2`… après le nom d'une autre session, jamais par-dessus) ; les titres suivent — `session.json` (et son `promotedTo`), `forge.json`, le `studio-team.json` d'Orkeon Studio (son seul `name` : tous les autres champs sont gardés, connus de cette version ou non), la ligne de titre et la commande d'installation de `FORGE.md`, l'en-tête des lanceurs ; `schedule/` est régénéré pour le nouveau chemin et le nouveau nom, et un enregistrement que le système exécute est réinstallé sous le nouveau nom, l'ancien retiré. Un nom dont le dossier est celui de l'équipe ne fait que la retitrer. Chaque étape est d'abord journalisée : quand l'une échoue — le disque refuse, le système refuse le nouvel enregistrement —, tout ce qui a été fait avant est remis en place, l'ancien enregistrement en dernier, et le verbe sort en 1 en disant que l'équipe n'a pas été renommée : `FORGE-RENAME-FAILED`, ou le `FORGE-SCHEDULE-REFUSED` du système. Un dossier déjà présent sous le nouveau nom — une autre équipe, un dossier, un fichier — est refusé avec `FORGE-RENAME-TAKEN`, qui dit ce qui s'y trouve ; un enregistrement qui exécute encore une équipe ne déclarant plus de planification refuse aussi le renommage (`FORGE-SCHEDULE-STILL-INSTALLED` : `unschedule` d'abord), puisqu'il resterait à lancer un dossier qui n'existe plus. Une copie est renommée sans que la session de son original soit jamais touchée, et un dossier qui ne contient aucune équipe — ni `forge.json`, ni `studio-team.json`, ni définition d'équipe — n'est jamais déplacé (`FORGE-TEAM-UNREADABLE`). Avec `--events` : les `warning`, `session.renamed` quand le dossier de session a bougé, `schedule.state` quand la planification a été réinstallée, puis `team.renamed` (`from`, `path`, `name`) ; un refus est un seul `error`, après lequel rien n'a changé. Le verbe ne prend aucune option hors `--name` et `--events`. C'est le « Renommer » d'Orkeon Studio, qui réécrit en plus son propre historique des lancements — la seule chose que le CLI ne possède pas.

**Codes de sortie et codes d'erreur.** `0` terminé (une session mise en pause par `--dry` comprise), `1` une erreur d'usage ou un refus, `2` une erreur inattendue, `130` Ctrl+C — la session est sauvegardée et reprenable. Un refus nomme son code sur stderr, et en mode `--events` dans un événement `error` (`code`, `message`, `recoverable`). En plus des codes ci-dessus, un cycle peut signaler `FORGE-BRIEF-INCOMPLETE` (l'entretien n'a produit aucun brief valide), `FORGE-FOLDERS-INVALID` (les dossiers confirmés enfreignent les règles, ou relient un dossier d'entrée que l'essai dans le processus ne pourrait pas lire — récupérable, ils sont proposés à nouveau), `FORGE-BLUEPRINT-INVALID` (aucun plan d'équipe valide), `FORGE-TOOL-UNKNOWN` (le plan nomme un outil que le catalogue du bac à sable n'offre pas), `FORGE-VALIDATION-FAILED` (le crew rendu échoue encore à la validation après les tentatives de réparation), `FORGE-BUDGET-EXHAUSTED` (une dimension du budget est épuisée — la session reste reprenable), `FORGE-SESSION-CORRUPT` (un fichier de session manquant ou illisible), `FORGE-PROMOTE-FAILED` (le dossier n'a pas pu être écrit — la session reste Ready) et `FORGE-STAGE-FAILED` / `FORGE-ENGINE-CRASHED` (une étape a échoué). Les verbes de planification ajoutent trois codes `warning` : `FORGE-SCHEDULE-NOT-OWNED` (l'enregistrement consigné appartient au dossier dont celui-ci est une copie, et n'est pas touché), `FORGE-SCHEDULE-OTHER-SYSTEM` (il a été fait sur un autre système d'exploitation) et `FORGE-SCHEDULE-FILES-KEPT` (l'enregistrement est retiré mais certains de ses fichiers n'ont pas pu être supprimés) ; `forge rename` un quatrième, `FORGE-RENAME-SIDECAR-UNREADABLE` (le `studio-team.json` de Studio n'a pas pu être lu, donc le nom qu'il consigne est resté tel quel).

## `orkeon usecases`

```bash
orkeon usecases search "je veux un résumé de mes mails chaque matin"  # les cas d'usage les plus proches
orkeon usecases search "summarize my emails every morning" --top 3
orkeon usecases list --category finance-trading --process parallel   # le catalogue, filtré
orkeon usecases show 03-email-pipeline --crew                         # une fiche, et son fichier de crew
orkeon usecases export 01-research-assistant --to ./research --lang fr   # un cas d'usage, en dossier d'équipe
```

Le catalogue des cas d'usage d'exemple : les 104 exemples numérotés d'`examples/`, chacun décrit par une fiche écrite en cinq langues ([usecases.json](https://github.com/Orkeon/orkeon/blob/main/examples/usecases.json)). L'outil embarque le catalogue lui-même — le manifeste, le fichier de crew de chaque exemple et son dossier `data/` — si bien que chaque sous-commande fonctionne hors ligne, ne lit rien sur le disque et n'appelle aucun LLM ; seul `export` écrit. Les exemples finance sont **référence seule** : on peut les chercher et les lire, pas les importer, car leurs crews dépendent d'un dossier `_tools/` partagé que l'outil n'embarque pas.

**`search <texte>`** classe le catalogue selon un besoin écrit en langage naturel, en français, anglais, espagnol, allemand ou chinois simplifié.

- **Par les termes** : BM25 sur le titre et le problème de chaque fiche dans les cinq langues, ses tags, ses outils et sa catégorie. La requête et les fiches sont normalisées de la même façon — minuscules, accents repliés (`resume` trouve `résumé`), chinois découpé en bigrammes de caractères —, si bien qu'une requête trouve ses termes dans la langue où elle est tapée.
- **Par le sens** : le modèle d'embeddings local (BGE-micro-v2, sur la machine) compare la requête au texte anglais de chaque fiche, et son classement est fusionné avec celui des termes par RRF. Le modèle ne lit que l'anglais (voir [Limites connues](./limitations.md)) : le sens n'est donc ajouté que pour les langues où le jeu d'or ([usecases.golden.yaml](https://github.com/Orkeon/orkeon/blob/main/examples/usecases.golden.yaml)) a mesuré un gain — aujourd'hui l'anglais seul (mesure du 2026-09-24 sur les textes en cinq langues : les termes seuls atteignent un rappel@5 de 1,00 dans chaque langue, et le sens n'améliore le classement qu'en anglais) ; le français, l'espagnol, l'allemand et le chinois sont cherchés par les termes. Le modèle se charge à la première recherche qui en a besoin — environ une seconde —, puis chaque recherche prend quelques millisecondes.
- **Sans le modèle** (ses fichiers vont dans `LocalEmbeddingsModel/default/` à côté du binaire ; `orkeon doctor` les vérifie), la recherche passe par les termes seuls et chaque réponse le dit. Elle ne se dégrade jamais en silence.

| Option | Description |
|---|---|
| `--top <n>` | Nombre de cas d'usage renvoyés (défaut 5). |
| `--lang fr\|en\|es\|de\|zh-Hans` | La langue de la requête (`zh` est accepté pour `zh-Hans`). Omise, elle est lue dans le texte — mots grammaticaux, lettres accentuées, caractères chinois — et des mots-clés qui ne trahissent rien comptent comme de l'anglais. Elle choisit le mode de recherche et les titres affichés. |
| `--events jsonl` | Répond par une ligne `usecases.results` sur stdout au lieu du rendu texte (`jsonl` est la seule valeur ; toute autre sort en 1). **Sans texte, mode session** : une requête par ligne de stdin, une réponse par requête, le modèle chargé une seule fois pour toutes, et la fin de stdin termine le processus avec le code 0. |

Chaque résultat porte l'`id` du cas d'usage, son `rank`, son `score` (BM25 par les termes, RRF en mode hybride — comparable au sein d'une même réponse seulement), la raison de la correspondance `reason` (`terms`, `meaning` ou `terms+meaning`), les termes trouvés `terms`, sa similarité `similarity` avec la requête en mode hybride, et son titre dans la langue de la requête. La réponse porte le mode employé `mode` (`bm25` ou `hybrid`), la langue et la façon dont elle a été établie (`langSource` : `option`, `detected` ou `default`), et `degraded`, la raison, quand le sens a été abandonné.

Le mode session est ce qui permet à Orkeon Studio de suggérer des cas d'usage pendant la frappe : le processus s'ouvre sur une ligne `usecases.ready` (taille du catalogue, langues, mode de chacune), puis répond à chaque requête avec le `correlationId` de la requête dans l'enveloppe.

```text
→ {"kind":"usecases.query","correlationId":"q1","text":"relancer les factures impayées","lang":"fr","top":5}
← {"v":2,"seq":2,"ts":"…","kind":"usecases.results","correlationId":"q1","query":"relancer les factures impayées","lang":"fr","langSource":"option","mode":"bm25","results":[{"rank":1,"id":"40-invoice-processing","score":7.8412,"reason":"terms","terms":["factures"],"title":"…"}]}
```

Une requête sans `top` ni `lang` prend le `--top` et la `--lang` de la ligne de commande. Une ligne qui n'est pas une requête est ignorée. Une requête qui ne peut pas s'exécuter — pas de `text`, une `lang` hors des cinq, un `top` inférieur à 1 — reçoit une ligne `error` portant son `correlationId` et le code `USECASES-QUERY-INVALID`, et la session continue. Les types d'événement sont déclarés une seule fois, dans `Orkeon.Constants.Protocol.UseCaseEventKinds`.

**`list`** imprime le catalogue : id, processus, titre, et les indicateurs `data` (données d'exemple), `web` (a besoin du réseau), `keys` (a besoin d'une clé tierce) et `reference only`. Les filtres se combinent : `--category` (`03-finance-trading`, ou `finance-trading`), `--process` (`sequential`, `hierarchical`, `parallel`, `consensual`, `graph`, `autonomous`), `--tag`. Une catégorie ou un processus inconnu est refusé, avec la liste des valeurs valides. `--lang` choisit les titres (défaut `en`). `--events jsonl` émet une ligne `usecases.catalog` qui contient chaque fiche en entier, sous les noms de champ du manifeste.

**`show <id>`** imprime une fiche : sa catégorie, son processus, ses agents et tâches, ses outils, ses tags, ce dont elle a besoin (réseau, clés), ses montages, si elle est importable, les fichiers que l'outil embarque pour elle, et son titre et son problème dans chaque langue écrite (`--lang` pour une seule). `--crew` ajoute le fichier de crew. `--events jsonl` émet une ligne `usecases.sheet`, avec `crew` sur demande. Un id inconnu sort avec le code 1 et `USECASES-UNKNOWN-ID` (une ligne `error` en mode `--events`).

**`export <id> --to <dossier>`** écrit un cas d'usage sous la forme d'un dossier d'équipe qu'Orkeon Studio importe tel quel (STUDIO-41) : `crew/config.yaml` — la crew de l'exemple, octet pour octet —, son dossier `data/` s'il en a un, un dossier derrière chacun de ses montages (`output/` pour toute crew qui écrit des fichiers), et `studio-team.json`, la fiche Studio qui nomme l'équipe d'après le titre du cas, la décrit par son problème — tous deux dans la langue de `--lang`, `en` par défaut — et enregistre les montages du manifeste relativement au dossier (`./data:/data:ro`, `./output:/output:rw`). Il n'y a pas de `forge.json` : aucune session d'atelier n'a produit l'équipe, et `forge reopen` en reconstruit une depuis `crew/` à la première modification de l'équipe. Seuls les montages du manifeste sont enregistrés — aucun dossier d'entrée n'est inventé. `--to` est créé s'il n'existe pas ; un dossier qui contient quoi que ce soit, ou un fichier, est refusé avec `USECASES-DESTINATION-NOT-EMPTY` — un export ne fusionne jamais —, et un cas « référence seule » avec `USECASES-NOT-IMPORTABLE`. `--events jsonl` répond par une ligne `usecases.exported` : `id`, `path`, `name`, `lang`, `files` (chaque fichier écrit, en relatif) et `mounts`. Le dossier se lance depuis l'intérieur — `orkeon run crew/config.yaml --mount ./data:/data:ro ./output:/output:rw`, comme la commande l'affiche — ou depuis Studio une fois importé, qui pose les montages lui-même.

Codes de sortie : `0` réponse donnée (réponse vide comprise — un `--tag` inconnu ne trouve simplement rien), `1` refus (id inconnu, option invalide, cas « référence seule » ou destination non vide à l'export), `2` erreur inattendue, `130` Ctrl+C. Les codes : `USECASES-UNKNOWN-ID`, `USECASES-OPTION-INVALID` (un `--lang` hors des cinq, un `--top` inférieur à 1, une recherche sans texte et sans `--events`, une catégorie ou un process inconnus), `USECASES-NOT-IMPORTABLE`, `USECASES-DESTINATION-NOT-EMPTY`, et en mode session `USECASES-QUERY-INVALID` et `USECASES-SEARCH-FAILED` (une requête a échoué ; la session continue) ; `USECASES-FAILED` est l'erreur inattendue. Un argument manquant ou une option inconnue reçoivent à la place l'aide des options, avec le code 1 et sans code d'erreur.

## `orkeon init`

Assistant de configuration. Génère un `appsettings.json` valide au chemin global par utilisateur (`%APPDATA%\Orkeon\appsettings.json` sous Windows, `$XDG_CONFIG_HOME/Orkeon/appsettings.json` — sinon `~/.config/Orkeon/appsettings.json` — sous Linux **et** macOS, qui n'utilise volontairement pas `~/Library/Application Support`) via un assistant interactif à 5 choix — `ollama`, `docker-model-runner`, `openai`, `custom`, `none` — ou en mode non interactif par flags, puis sonde l'endpoint (sauf `--no-probe`).

| Option | Description |
|---|---|
| `-p, --provider <preset>` | `ollama` \| `docker-model-runner` \| `openai` \| `custom` \| `none` (insensible à la casse). Sans elle, l'assistant pose la question — et une entrée standard non interactive est refusée avec le code 1. |
| `-u, --base-url <url>` / `-m, --model <id>` | Endpoint et modèle. Requis pour `custom` ; les presets ont leurs défauts (ci-dessous). |
| `-k, --api-key-env <nom>` / `--api-key <valeur>` | La variable qui contient la clé d'API — écrite dans le fichier en `Llm:ApiKeyEnvVar`, que chaque run lit, sauf si c'est `ORKEON_Llm__ApiKey` (le défaut), que le runtime lit nativement ; la sonde de `init` la lit aussi — ou une clé stockée en clair dans le fichier (déconseillé). Voir [la variable par fournisseur](./llm-providers-comparison.md). |
| `--path <fichier>` | Écrire ailleurs qu'au chemin global par utilisateur. Un dossier reçoit un `appsettings.json`. |
| `-f, --force` | Écraser un fichier existant. |
| `--no-probe` | Sauter la sonde de l'endpoint. |

| Preset | URL de base | Modèle | Clé d'API |
|---|---|---|---|
| `ollama` | `http://localhost:11434` | `llama3.2` | aucune — `--api-key` et `-k` sont ignorés |
| `docker-model-runner` | `http://localhost:12434/engines/llama.cpp/v1` | `ai/granite-4.0-h-tiny` | la valeur de remplissage `not-needed`, écrite en clair (`--api-key` la remplace) |
| `openai` | `https://api.openai.com/v1` | `gpt-5.6-sol` | lue dans `ORKEON_Llm__ApiKey`, ou dans la variable que nomme `-k` (`Llm:ApiKeyEnvVar`), jamais écrite — sauf `--api-key` |
| `custom` | requise | requis | comme `openai` |
| `none` | — | — | — |

Le fichier ne contient qu'une section `Llm` (`Model`, `BaseUrl`, puis `ApiKeyEnvVar` quand `-k` nomme une autre variable que `ORKEON_Llm__ApiKey`, ou `ApiKey` quand une clé est écrite en clair) ; `none` n'écrit aucune section `Llm`, seulement un `_comment` qui dit que les runs se replient sur le fournisseur écho `<undefined-llm>`. La sonde liste les modèles de l'endpoint (le catalogue d'Ollama pour `ollama`, celui d'OpenAI sinon) avec un délai de 5 secondes ; une sonde en échec est un avertissement — le fichier est écrit quand même, et le code de sortie reste `0`. Codes de sortie : `0` écrit, `1` une option erronée, un fichier déjà présent sans `--force`, un assistant interrompu, `2` une erreur inattendue, `130` Ctrl+C.

```bash
orkeon init --provider ollama --model llama3.2 --no-probe
```

## `orkeon llm`

Deux verbes contre un endpoint fournisseur réel.

**`orkeon llm probe`** — déroule le protocole de test LLM contre un fournisseur et archive éventuellement la trace de campagne. Options clés : `-p, --provider` (requis : `openai | anthropic | ollama | azure | together | qwen | deepseek | kimi | mistral | huggingface | zai | gemini | grok | minimax | openrouter | mammouth`), `-m, --model`, `-u, --base-url` (requis pour Azure), `--api-version` (mode déploiement Azure), `--workspace-id` (clés à portée de workspace — les clés identity-linked d'Anthropic l'exigent), `-k, --api-key-env` (défaut `ORKEON_LLM_API_KEY` — la clé elle-même n'est jamais acceptée sur la ligne de commande), `--modes` (séparés par des virgules, ex. `M1,M2,M8` ; défaut : tous), `--archive <rép>` (où le rapport de campagne est écrit ; rien n'est archivé sans elle), `--format md|json` (défaut `md`), `--commit <sha>` (le commit court de l'arbre testé, consigné dans le rapport), `--timeout` (secondes par requête, défaut 180), `--temperature` (défaut 0), `--thinking-effort` (effort de raisonnement de base, ex. `none` — certains modèles refusent les function tools en raisonnant), `--m7-effort` (effort utilisé par la sonde thinking M7, défaut `low` — pour les modèles dont l'ensemble supporté l'exclut).

**`orkeon llm models`** — liste les modèles servis par un fournisseur. Options : `-p, --provider` (requis), `-u, --base-url`, `-k, --api-key-env`, `-f, --filter` (glob shell), `--json`.

```bash
ORKEON_LLM_API_KEY=... orkeon llm probe -p deepseek --modes M1,M2 --format json
orkeon llm models -p ollama --filter 'llama*'
```

## `orkeon rag`

Trois verbes sur le sous-système RAG (`ingest`, `search`, `eval`). Tous partagent les options d'hôte de `run` : `-s/--settings`, `-m/--mount`, `--allow-external-mounts`, `-v/--verbose`. Les sources relatives se résolvent contre un montage automatique `{cwd} → /workspace:ro` ; l'état atterrit dans `{cwd}/.orkeon → /output:rw`.

**`orkeon rag ingest`** — ingestion incrémentale (les sources inchangées sont sautées) : `-c, --collection` (requis), `--source <chemin|glob|url>` (requis ; plusieurs sources séparées par des espaces derrière un seul flag, globs résolus via le système de fichiers virtuel, une adresse `http(s)://` passée telle quelle au chargeur web — son `?` ou son `*` ne sont pas un motif), `--chunking recursive|sentence|structural|semantic` (le défaut du pipeline s'il est omis), `--reindex` (réindexation complète — seule issue après un changement de modèle/dimension d'embedding).

**`orkeon rag search`** — pose une question, imprime la réponse fondée avec citations et scores : `<question>` positionnelle, `-c, --collection` (requis), `--top-n` (défaut 5).

**`orkeon rag eval`** — évalue une collection contre un jeu de données de référence (recall@k, MRR, groundedness) et écrit des rapports markdown/JSON ; le dossier `corpus` du jeu de données est d'abord ingéré, de façon incrémentale : `-d, --dataset` (requis), `-c, --collection` (défaut : la collection du jeu de données, sinon `rag-eval-<nom du jeu>`), `--profile fast|balanced|quality|adaptive|corrective|default` (défaut `default` = le `Orkeon:Rag:Profile` configuré) ou `--compare fast,balanced,…`, `-k` (défaut 5), `--llm-judge`, `--offline` (zéro réseau : stub extractif déterministe, aucune clé LLM nécessaire — il répond à la place de tout modèle, `Orkeon:Rag:LlmProfile` compris), `--no-ingest`, `--reindex`, `--min-recall` / `--min-mrr` (portes anti-régression, sortie 1 sous le seuil), `--output` (défaut `/output/rag/eval`, soit `./.orkeon/rag/eval`).

```bash
orkeon rag eval --dataset examples/rag/eval/golden.yaml \
  --compare fast,balanced,quality,corrective,adaptive --offline
```

## `orkeon email`

```bash
orkeon email accounts [--settings <fichier>] [--json]   # les comptes déclarés, leurs droits, si chacun est prêt
orkeon email login <compte> [--settings <fichier>]      # connecter un compte OAuth2 et enregistrer ses jetons
orkeon email logout <compte> [--settings <fichier>]     # oublier les jetons enregistrés d'un compte OAuth
orkeon email check <compte> [--settings <fichier>]      # se connecter, s'authentifier, lister les dossiers
```

Le côté opérateur des outils e-mail ([guide](../guides/email.md)) : ce qui est déclaré sous
`Orkeon:Tools:Email`, la seule étape interactive qu'exige un compte OAuth2, et une vérification
de connexion. Les agents ne les lancent jamais — un outil qui ne trouve aucun jeton utilisable
répond « run `orkeon email login <account>` ».

- **`accounts`** liste chaque compte déclaré — son préréglage, comment il lit et envoie, comment
  il se connecte, ses droits, s'il est le compte par défaut — et dit `ready`, ou ce qu'il faut
  corriger : une déclaration invalide, une variable de mot de passe ou de secret client non
  définie, une connexion encore à faire. La commande n'ouvre aucune connexion et n'affiche aucun
  secret ; `--json` écrit la même liste en JSON, sous les noms qu'utilise `email_accounts`
  (`name`, `address`, `provider`, `reads`, `sends`, `rights`, `auth`, `default`, `ready`,
  `problem`).
- **`login`** connecte un compte OAuth2. Un compte Microsoft passe par le flux par code
  d'appareil : la commande affiche l'adresse de vérification que renvoie Microsoft et un code,
  et attend pendant que vous vous connectez depuis n'importe quel navigateur. Un compte Google
  passe par le code d'autorisation avec PKCE : la commande affiche l'adresse d'autorisation de
  Google et écoute sur un port libre de `127.0.0.1` ; quand le navigateur ne peut pas atteindre
  cette machine (WSL, un conteneur, une session SSH), collez dans le terminal l'adresse où le
  navigateur aboutit. Les jetons vont dans la racine interne `/credentials` du runner
  ([où vivent les jetons](../guides/email.md#où-vivent-les-jetons)). Un compte à mot de passe
  n'a rien à connecter et est refusé.
- **`logout`** supprime les jetons enregistrés d'un compte OAuth, et le dit quand il n'y en avait
  pas ; un compte à mot de passe n'en a pas et est refusé.
- **`check`** se connecte, s'authentifie et liste les dossiers, puis affiche leur nombre et les
  compteurs de la boîte de réception.

`-s, --settings <chemin>` se résout comme pour `orkeon run`, ancré sur le répertoire courant :
le fichier explicite, sinon `appsettings.json` dans le répertoire courant, sinon un
`appsettings/appsettings.json` trouvé en remontant, sinon le fichier utilisateur d'`orkeon init`,
sinon les seules variables d'environnement `ORKEON_*` — ce que laisse aussi un chemin explicite
qui n'existe pas, avec un avertissement. Le fichier retenu est nommé sur stderr
(`Using settings: …`).
Codes de sortie : `0` succès, `1` usage, configuration ou refus (un compte inconnu, une variable
non définie, une connexion à faire — fournisseur qui n'a délivré aucun jeton de rafraîchissement
compris —, un droit ou une capacité manquants), `2` ce qu'ont fait le réseau ou le serveur (un
échec de connexion, des identifiants ou une autorisation refusés par le fournisseur) ou une
erreur inattendue (`ORKEON_DEBUG=1` en imprime la trace de pile), `130` Ctrl+C. Le verbe est reconnu avant la détection d'un chemin de crew, comme tous les verbes : un
dossier de crew nommé `email` se lance avec `orkeon run email`.

## `orkeon typings`

```bash
orkeon typings                   # écrit orkeon.d.ts et orkeon-cli.d.ts dans ./.orkeon/
orkeon typings --out crews/.orkeon
```

Écrit les typings TypeScript que porte ce build de l'outil, pour votre éditeur : `orkeon.d.ts` (le [DSL de scripting](./scripting-dsl.md#réglage-de-léditeur) `.ork.ts`) et `orkeon-cli.d.ts` (les [commandes `*.cmd.ts`](../architecture/cli-ts-commands.md) du REPL). Les deux sont embarqués dans l'outil : un `dotnet tool install` suffit — ni clone, ni build. `-o`/`--out <dossier>` choisit le dossier (`./.orkeon` par défaut, créé s'il manque) ; les fichiers existants sont écrasés, relancez donc la commande après une mise à jour de l'outil. Un script commence alors par `/// <reference path="./.orkeon/orkeon.d.ts" />`, chemin relatif au script. Hors ligne. Codes de sortie : `0` écrit, `1` un argument inconnu ou `--out` sans dossier.

## `orkeon mcp`

```bash
orkeon mcp serve [--settings <fichier>] [--tools a,b,…]
```

**`orkeon mcp serve`** sert les outils d'un hôte Orkeon à un client MCP sur stdio — comme Claude Desktop ou un éditeur démarre un serveur MCP local : le client lance la commande, écrit des messages JSON-RPC sur son stdin, un par ligne, et lit les réponses sur son stdout ; fermer stdin arrête le serveur. L'hôte est celui que construit `orkeon run` — les réglages, résolus comme ceux d'`orkeon run` depuis le répertoire courant (`-s, --settings <chemin>` nomme le fichier), leurs montages, les outils intégrés et les serveurs MCP qu'ils déclarent —, et ce qui est servi est ce qu'imprime `orkeon run --list-tools` pour les mêmes réglages, `human_input` à part. `--tools a,b,…` ne sert que les outils nommés ; un nom que l'hôte n'a pas refuse le démarrage. Chaque `tools/call` franchit le point d'invocation des appels d'un agent de crew — garde, troncature, assainisseur de résultat, audit — sous l'appelant `mcp`. Stdout ne porte que le protocole : journaux, avertissements, `--help` et erreurs d'usage vont sur stderr. Codes de sortie : `0` le client a fermé le flux (ou `--help`), `1` une erreur d'usage, un réglage refusé ou un nom de `--tools` que l'hôte n'a pas, `2` une erreur inattendue. Une configuration client et le détail : [Intégration MCP](../architecture/mcp.md#servir-les-outils-avec-orkeon-mcp-serve).

## `orkeon doctor`

Diagnostic d'installation : dit en moins de 15 secondes ce qui fonctionne et ce qui manque, en table ✅/⚠️/❌ ou en `--json` (schéma stable `{check, status, detail}` pour la CI). Dix vérifications, dans cet ordre : `dotnet-runtime`, `appsettings`, `llm-config`, `llm-profiles`, `llm-reachability`, `esbuild`, `local-embeddings`, `onnx-reranker`, `tree-sitter`, `workspace-write` — plus, après `llm-profiles`, une ligne `llm-profile-key` (`warn`) par profil dont l'`ApiKeyEnvVar` nomme une variable posée nulle part ; chaque `status` vaut `ok`, `warn` ou `fail`. `llm-config` se termine par l'origine de la clé du défaut (`API key from the variable named by Llm:ApiKeyEnvVar (user environment)` — jamais la clé ni le nom de la variable), avertit quand cette référence ne résout rien, et échoue quand la section ne se lit pas — une `ApiKey` écrite `${NOM}`, une référence qui n'est pas un nom de variable, une `BaseUrl` invalide —, comme un runner refuserait de démarrer ; `llm-profiles` liste chaque profil avec l'origine de sa clé ; `llm-reachability` interroge le catalogue avec la clé qu'un run utiliserait. `--json` est la seule option : les settings sont trouvés par la chaîne d'`orkeon run`, ancrée au répertoire courant, plus les variables d'environnement `ORKEON_*` — c'est aussi là que la vérification `esbuild` lit `Orkeon:Scripting:Toolchain:EsbuildPath`. L'outil dotnet ne livre pas esbuild : un ⚠️ sur cette vérification dit comment l'obtenir (`npm install -g esbuild`, `ORKEON_ESBUILD_PATH` ou `EsbuildPath`), et ses deux détails nomment `orkeon typings` pour les typings d'éditeur. Codes de sortie : `0` tout vert ou avertissements seuls, `1` au moins une vérification en échec (ou une option invalide), `2` une erreur inattendue, `130` Ctrl+C.

```bash
orkeon doctor --json
```

## `orkeon-repl` — la console interactive séparée

`orkeon-repl` est un **outil distinct** construit depuis `src/apps/Orkeon.ConsoleApp` (commande dotnet tool `orkeon-repl`) : un REPL interactif complet pour piloter agents, crews et outils depuis une console Terminal.Gui à deux volets (logs + REPL), avec toute la pile du framework câblée — outils intégrés, RAG, analyse de code, embeddings locaux — et des commandes scriptées en TypeScript. Il ne partage volontairement pas le nom d'assembly `orkeon`.

| Option | Description |
|---|---|
| `--ui tui\|plain\|auto` | La console : la TUI à deux volets, ou une console en lignes simples. `auto` (le défaut) choisit la TUI sur un terminal interactif, et la console simple quand `CI=true`, quand stdin ou stdout est redirigé, ou quand `TERM` n'est pas défini sous Linux. Une valeur inconnue sort en 2. |
| `--repl-wrap on\|off` | Retour à la ligne dans le volet REPL (défaut `on` ; `true`/`false`/`1`/`0` sont acceptés). Une valeur inconnue sort en 2. |
| `--runner=scripted-commands` | Démarre dans le REPL des commandes scriptées au lieu du menu principal. |
| `--commands-dir <chemin>` / `--no-script-commands` / `--strict-commands` | Où trouver les commandes `*.cmd.ts`, ou aucune, ou l'échec immédiat sur une commande cassée. |
| `--crews-dir <chemin>` | Où `script-host` résout une crew par son nom. |
| `--settings <chemin>` / `--mount <spec>` | Des fichiers de settings supplémentaires (les derniers l'emportent) et des montages VFS. |

Les quatre dernières lignes sont détaillées dans [Commandes CLI en TypeScript](../architecture/cli-ts-commands.md#options-cli) ; chaque option à valeur accepte `--x valeur` et `--x=valeur`, et peut être répétée. Les options standard de l'hôte .NET (surcharges de configuration `--Cle=Valeur`) s'appliquent aussi.

**Réglages.** Le REPL lit les réglages que lisent les runners (STUDIO-49) : les fichiers `--settings` — sinon le fichier global qu'écrit `orkeon init` ; un fichier nommé sur la ligne de commande le remplace, comme pour `orkeon run` — par-dessus son propre `appsettings.json`, puis les variables d'environnement `ORKEON_`, préfixe retiré (`ORKEON_Llm__ApiKey` est `Llm:ApiKey` ici comme dans chaque runner), par-dessus celles sans préfixe ; la ligne de commande reste en dernier. Sa section `Llm` et ses profils sont lus par le lecteur des runners, `ApiKeyEnvVar` compris, et le volet des journaux dit une fois d'où vient chaque clé, avec un avertissement par référence vers une variable posée nulle part.
